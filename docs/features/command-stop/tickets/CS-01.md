# CS-01: 실행 명령 신원(run identity)과 pidfd pin 기반

명세: [../SPEC.md](../SPEC.md) s1. Scheduling·의존성·resource·write scope·gate supplier: [../PLAN.json](../PLAN.json)의 CS-01. 상태·실제 assignment는 Root 운영 기록에서만 관리한다.

## 제공할 동작

stop과 Ctrl+C가 공통으로 쓰는 읽기 전용 기반이다. 사용자에게 보이는 기능은 아직 없다.

1. `PersistentShell.run_identity()` / `HostShellPort.run_identity()`: 실행 중인 managed 요청의 신원(`request_id`, host shell parent, supervisor, command child의 `pid`+`start_ticks`, `child_group`, `session`, `uid`, `boot_id`, `phase`)을 `lifecycle`·`/proc`에서 읽어 돌려준다. 요청이 없거나 끝났으면 `None` 또는 `phase="ended"`. lifecycle 상태기계와 `submit`/`poll` 동작은 바꾸지 않는다.
2. 새 `src/workbench/backend/command_stop.py`의 기반부: `StopEnvironment`(시계·대기·`/proc` 조회·pin·signal을 묶은 port, 기본 `LinuxStopEnvironment`), `ProcessPin`(pidfd를 열고 `/proc`를 다시 읽어 같음을 확인; `verify()`; 확인 후에만 `send(signum)`; 불일치는 `stale`, 종료는 `ended`, uid 다름은 `different_uid`), `scan_tracked(identity)`(supervisor 후손 ∩ host shell session + 같은 pgrp를 `tracked`, 다른 session 후손을 `left_session`으로 분류; ppid 전수 조사; supervisor·host shell parent·backend 등 금지 pid 제외).

## 수락 기준

- CS-AC-08(부분): 대상 PID 재사용·시작 시각 불일치·검증 중 신원 변경 시 신호가 나가지 않고 `stale`/`identity_changed`가 반환된다. 신호 직전 재확인이 `ProcessPin.send` 안에 있다. (stop 전체 흐름에서의 `stale` 결과는 CS-02가 완성한다.)
- 이 ticket 고유 관측: 실제 PTY 명령의 identity 값이 테스트가 `/proc`에서 직접 읽은 값과 일치하고, `tracked`/`left_session` 분류가 실제 프로세스 구조와 일치한다.

## 계약과 맥락

- SPEC "추적 범위와 잔존 확인", "신원·신호 불변식" 1~3, 7. 선례: `panes._pin_member`, `_OwnedSession`, `app/recovery.py` `SurvivorRegistry._pin`, `_descendant_pids`(비-main thread 자식 누락 때문에 쓰지 않음).
- identity 출처: `lifecycle`의 `supervisor_pid`/`child_pid`/`child_group`, transport의 `_supervisor_start`·`_child_start`(없으면 `None` = 아직 준비 전/이미 종료).
- 이 ticket은 `command_stop.py`를 새로 만든다. 이후 ticket이 같은 파일을 확장하므로 공개 이름(위 목록)을 안정적으로 둔다.

## 검증

Seam S6(신규, 2026-10-21 사용자 확정) + 실제 `PersistentShell`/실제 프로세스. 독립 기대값은 테스트가 직접 띄운 프로세스의 `/proc/<pid>/stat`(ppid·pgrp·session·starttime)와 `os.getuid()`, `read_boot_id()`다. 생산 코드의 scan 결과로 expected를 계산하지 않는다.

한 behavior씩 RED→최소 GREEN:
1. 실행 중 `sleep 30` 명령의 `run_identity()`가 parent/supervisor/child pid·start·pgrp(= child pid)·session(= parent pid)을 `/proc` 값과 같게 돌려준다. 요청 전은 `None`, 종료 후는 `phase="ended"`.
2. `ProcessPin`: 올바른 start ticks면 pin 성공·`send(0)`류 무해 확인 가능, 틀린 start ticks면 `stale`(신호 없음), 이미 종료한 pid면 `ended`.
3. 신호 직전 신원 변경: 오류 주입 `StopEnvironment`(S7 형태)가 `verify` 직후 start ticks를 바꾸면 `send`가 신호를 보내지 않고 `identity_changed`를 반환한다(실제 프로세스는 계속 산다).
4. `scan_tracked`: `bash -c 'sleep 60 & setsid sleep 61 & wait'` 명령에서 `sleep 60`·bash는 `tracked`, `setsid sleep 61`은 `left_session`, supervisor·host shell parent·backend pid는 어느 쪽에도 없다. 종료된 구성원은 제외.

작성 범위: `src/workbench/backend/command_stop.py`(신규), `src/workbench/terminal/shell_persistent/adapter.py`, 필요 시 `src/workbench/terminal/shell_g2/lifecycle.py`(읽기 접근자만), `src/workbench/backend/panes.py`(`HostShellPort.run_identity`), `tests/terminal/test_run_identity.py`, `tests/backend/test_command_stop_pins.py`. `*_independent*`은 건드리지 않는다.

명령: `env PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src .venv/bin/python -m unittest discover -s tests/terminal -p 'test_run_identity*.py'`; `... discover -s tests/backend -p 'test_command_stop_pins*.py'`; 회귀 `... discover -s tests/terminal -p 'test_persistent_shell*.py'`, `... -s tests/backend -p 'test_panes.py'`.

프로세스·신원 작업이므로 독립 `test_designer`가 요구(SPEC 불변식)에서 먼저 시나리오를 도출해 보강한다. 이후 단위 review 1회. PLAN gate `CS-G01`(runtime, supplier CS-01). 이후 통합 coverage는 CS-02·CS-10.

## 범위 밖과 중단 조건

신호 단계, 인가, journal, 도구 연동은 하지 않는다. lifecycle 이벤트 문법이나 supervisor 코드를 바꿔야 identity를 얻을 수 있으면 멈추고 `needs_reroute`/`needs_oracle`로 반환한다(상태기계 변경은 이 ticket 범위가 아니다). 테스트가 띄운 process·temp dir은 정리한다.

후보 id, 변경 경로, 정확한 명령·결과, behavior별 RED 실패 메시지·최소 변경·GREEN, `run_identity` 반환 필드 목록(CS-02/07이 소비), 한계, 소유 process 종료 확인.
