# CS-02: Worker가 자기 명령을 SIGINT로 stop (`terminal.stop`)

명세: [../SPEC.md](../SPEC.md) s1. Scheduling·의존성·resource·write scope·gate supplier: [../PLAN.json](../PLAN.json)의 CS-02. 상태·실제 assignment는 Root 운영 기록에서만 관리한다.

## 제공할 동작

Worker가 `terminal {command: null, stop: "<command_id>"}`로 자기 명령을 멈추면, 백엔드가 pidfd로 신원을 고정한 tracked 구성원에 SIGINT를 보내고 소유자가 종료를 관측할 때까지(또는 시한까지) 기다려 최종 상태를 반환한다. 이 ticket은 `CommandStopService`/`StopEpisode`의 뼈대(등록부, episode thread, 호출 대기, SIGINT 단계, 결과 조립, 기본 감사 레코드)를 만든다. SIGTERM/SIGKILL, 반복 요청, unknown 정정은 CS-03/04가 채운다. 따라서 이 후보 단독으로는 출시 대상이 아니다(SIGINT를 무시하는 명령은 시한 뒤 `unknown`).

## 수락 기준

- CS-AC-03: stop 호출이 종료 확인(또는 시한)까지 기다린 뒤 `exited`, `exit_code`(130), `signal`(2), `signal_name`("SIGINT")를 반환. 대기 중 다른 경로 조회에서 `stopping`이 보인다. 요청 수락만으로 성공을 보고하지 않으며 `terminal_done` 통지는 별도로 한 번 전달된다.
- CS-AC-07: 없는 id → `not_found`, 이미 끝난 id → `already_exited`(마지막 종료 상태). 어떤 프로세스에도 신호 없음.
- CS-AC-08: 식별한 신원이 틀리면(주입) `stale`, 신호 없음.
- CS-AC-09: 명령이 host terminal을 점유한 동안에도 처리되고, 같은 시점 새 `terminal` 명령은 기존대로 `terminal_command_running`이며 stop 때문에 host terminal에 입력하지 않는다.
- CS-AC-19: host shell과 Workbench·OMP는 종료되지 않고 명령 종료 뒤 shell이 사용자에게 돌아오며 로그가 보존된다.
- CS-AC-20(부분): `command_stop_requested/target/signal/finished` 및 거절·not_found 레코드가 SPEC 필드로 journal에 남는다.

## 계약과 맥락

- SPEC "Worker: `terminal` 도구의 stop 인자", "결과 계약", "명령 상태 표면", "단계와 타이머", "감사 기록". 선행 CS-01의 `run_identity`, `ProcessPin`, `scan_tracked`를 소비한다.
- `TerminalService`가 `StopTarget` provider가 된다: `_Command`에 `port`(HostShellPort)를 보관하고 종료 관측 hook으로 `CommandStopService.command_ended(command_id, result)`를 부른다. `_follow`의 기존 완료 경로와 `terminal_done` 통지 로직은 바꾸지 않는다(stop 호출은 waiter가 아니다).
- `validate_terminal_arguments`가 `stop`(uuid 또는 null/빈 문자열)을 받고 `stop`+문자열 `command`를 거절한다. `RUNNING_DETAIL`의 "사용자가 host terminal에서 멈출 수 있다" 문구에 stop 안내를 더한다.
- `Backend`가 `CommandStopService`를 만들고 `TerminalService`에 연결한다(`service.py` 구성부만).
- 호출 대기 `CALL_WAIT=25 s`, 정책 상수는 `StopPolicy`로 주입(테스트는 줄인 값).

## 검증

Seam S2(실제 PTY `ShellPane`+`HostShellPort`+`TerminalService`, 기존 `tests/backend/test_flow_terminal.py` 패턴) + 입력 검증은 fixture. 독립 기대값: 테스트 자신이 띄운 `sleep` 명령의 종료 코드 128+2, `/proc`에서 읽은 pid의 소멸, 정책 상수, 입력한 command_id. 생산 formatter 출력으로 expected를 만들지 않는다.

한 behavior씩 RED→최소 GREEN:
1. `validate_terminal_arguments`: `stop` 허용, 빈 문자열은 미사용, `stop`+`command` 문자열 거절(필드 이름만, 값 비노출), 미지 필드는 계속 거절.
2. 실행 중 `sleep 60`에 `stop` → `exited` 130/2/SIGINT, `signals==[SIGINT]`.
3. 호출이 대기하는 동안 `terminal {command:null}` 조회가 `stopping`, 새 `terminal {command:"echo x"}`는 `terminal_command_running`이고 pane에 새 입력이 없다.
4. 종료 뒤 `terminal_done` 통지(fake notify)가 정확히 한 번, stop 호출이 그것을 소모하지 않는다.
5. 없는 id·종료된 id → `not_found`/`already_exited`, 동시에 도는 다른 프로세스에 영향 없음.
6. identity 불일치 주입 → `stale`, 대상 생존.
7. 종료 후 `input_owner==user`·`manual_prompt` 복귀, 로그 파일 존재, backend·OMP pid 생존.
8. journal 레코드 필드(SPEC) 존재, 환경 값·argv 없음.

작성 범위: `src/workbench/backend/command_stop.py`, `src/workbench/backend/flow_terminal.py`, `src/workbench/backend/service.py`(구성), `tests/backend/test_command_stop_terminal.py`. `*_independent*` 제외.

명령: `env PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src .venv/bin/python -m unittest discover -s tests/backend -p 'test_command_stop_terminal*.py'`; 회귀 `... discover -s tests/backend -p 'test_flow_terminal*.py'`, `-p 'test_terminal_*.py'`, `-p 'test_cd70_followups.py'`.

프로세스·신호·신원 작업이므로 독립 `test_designer` 검증 필수. PLAN gate `CS-G02`(runtime). 이후 통합 coverage는 CS-10(실제 시간 구간·OMP).

## 범위 밖과 중단 조건

SIGTERM/SIGKILL, idempotency, unknown 정정, Manager 도구, 인가 매트릭스, 실험, bridge, Ctrl+C는 하지 않는다. 필요한 호출 가능성이 `_follow`/`HostGate` 변경을 요구하면 멈추고 `needs_reroute`(이 ticket은 소유자 완료 경로를 바꾸지 않는다). 테스트 process·temp dir 정리.

## 출력

후보 id, 변경 경로, 정확한 명령·결과, behavior별 RED 실패 메시지와 GREEN, `StopTarget`·`StopEnvironment` 공개 시그니처(CS-03/04/05/09 소비), 한계, 소유 process 종료 확인.
