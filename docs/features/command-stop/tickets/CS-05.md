# CS-05: Manager `stop_command`, 인가 매트릭스, 재시작·취소·일시정지 중 stop

명세: [../SPEC.md](../SPEC.md) s1. Scheduling·의존성·resource·write scope·gate supplier: [../PLAN.json](../PLAN.json)의 CS-05. 상태·실제 assignment는 Root 운영 기록에서만 관리한다.

## 제공할 동작

1. Manager 전용 도구 `stop_command {command_id, reason}`의 backend 구현: `Backend._tool_request` → `_recovery_tool` 경로(`stop_survivor` 선례), 인자 검증(`validate_stop_command_arguments`), `reason` 환경 값 검사, 같은 tool call key 재전송은 캐시. 사용자 승인 없이 SIGINT→SIGTERM→SIGKILL을 진행하고 `requested_by=manager`를 기록한다. Worker `terminal` 명령(이 ticket) 대상.
2. `CommandStopService`의 인가 규칙: 등록부에서 command_id의 owner를 찾아 요청자와 비교. 거절은 신호 없이 이유와 함께 반환·기록: Worker가 Manager 명령(provider 부재 시 가짜 owner) → `refused: not_owner`, 이전 backend 시작분 → `refused: previous_backend_command`(→ `stop_survivor`).
3. Worker role 기준 소유권: `restart_worker`로 새 session이 된 뒤에도 이전 session이 시작한 명령을 새 Worker가 stop. 닫힌(`cancelled`) Task의 남은 명령도 Worker가 stop하며 Task를 다시 열지 않고 감사 기록에 `task_id`·`task_status`를 남긴다.
4. 일시정지·boot 확인 전 보류 중에도 stop은 처리되고 새 명령·자동 전달 보류는 그대로다.
5. Manager가 멈춘 Worker 명령의 `terminal` 결과·`terminal_done`·`commands_run`에 `stopped_by`·마지막 `signal`이 붙는다(기술 보완).

## 수락 기준

CS-AC-06(거절 사례), CS-AC-11(Manager stop, 사용자 승인 없음, 요청자 `manager`, 최종 상태 반환), CS-AC-13(검증 못 한 프로세스는 Manager 자체 판단 stop 불가), CS-AC-14(재시작 뒤 새 Worker가 stop, 소유자 표기 role `worker`), CS-AC-15(닫힌 Task의 명령 stop), CS-AC-22(일시정지·boot 보류 중 stop 처리), CS-AC-20(부분: 요청자 `manager|worker`, 거절 이유, `task_id`).

## 계약과 맥락

- SPEC "Manager: `stop_command`", "인가 매트릭스", "결과 계약"(`refused`), "감사 기록". 선행 CS-03의 단계·잔존 로직을 그대로 쓴다(Manager 요청도 같은 episode).
- `flow_recovery.py`의 `MANAGER_TOOLS`에 `STOP_COMMAND_TOOL="stop_command"`를 추가한다. 도구 호출 대기는 `terminal.stop`과 같은 `CALL_WAIT`.
- 일시정지 판정은 `automation`/`hold`와 무관하게 stop 경로에서 읽지 않는다(새 명령 경로의 `_paused_now`/`_held_now`는 건드리지 않는다).
- 실험 명령 provider는 CS-09가 붙인다. 이 ticket의 인가 단위 테스트는 가짜 provider로 owner=manager인 대상을 사용한다.

## 검증

Seam S3(인가 규칙, 가짜 provider) + S2(실제 PTY로 Manager 도구 경유 stop, `Backend._tool_request` 또는 service fixture). 독립 기대값: BRIEF 매트릭스, 테스트가 띄운 명령의 종료 코드(143/137), 테스트가 만든 session id·Task 상태.

RED→GREEN 순서:
1. 거절 매트릭스(S3): worker→manager 소유 id는 `refused: not_owner`, 모르는 id는 `not_found`, 이전 backend 시작분(journal에 started만 있고 현재/등록부에 없음)은 `refused: previous_backend_command`; 모두 신호 0건, `command_stop_refused` 기록.
2. Manager `stop_command`로 SIGINT 무시 Worker 명령이 SIGTERM/SIGKILL까지 가서 종료, `requested_by=="manager"`, 사용자 승인 요청 없음. Worker가 `stop_command`를 부르면 `tool_not_allowed_for_role`. `reason`에 환경 변수 값이 있으면 거절.
3. Worker의 `terminal` 결과/`terminal_done`에 `stopped_by: "manager"`.
4. 재시작: session A가 시작한 명령이 session B 호출로 stop됨(`owner=="worker"`).
5. 닫힌 Task: TaskFlow로 free-work Task를 취소한 뒤 Worker stop 성공, Task는 닫힌 채, 새 `terminal` 명령은 기존 규칙 그대로, journal에 `task_id`+`task_status:"closed"`.
6. 일시정지(`paused`)와 boot 보류(`held`) 중 stop 처리, 같은 시점 새 명령은 `paused`/`held`.

## 범위 밖과 중단 조건

실험 provider, bridge.ts, Ctrl+C는 하지 않는다. Manager 도구를 `stop_survivor` 흐름과 합치거나 이전 backend 생존자에 신호를 보내게 하는 변경이 필요해지면 멈추고 `needs_reroute`(C-D71 (1) 유지가 승인 조건).
