# CS-06: OMP bridge 도구 schema·timeout과 model-facing 안내

명세: [../SPEC.md](../SPEC.md) s1. Scheduling·의존성·resource·write scope·gate supplier: [../PLAN.json](../PLAN.json)의 CS-06. 상태·실제 assignment는 Root 운영 기록에서만 관리한다.

## 제공할 동작

Python backend의 stop 계약(SPEC "Worker: terminal 도구의 stop 인자", "Manager: stop_command")을 OMP extension이 노출한다. 이 ticket은 계약-우선 병렬 작업이다: 공유 인터페이스는 SPEC에 고정된 인자 이름·결과 형태·timeout 상수이고, backend와의 결합은 CS-10의 교차 검증이 확인한다.

1. `bridge.ts`: `TERMINAL_PARAMETERS`에 `stop`(`OPTIONAL_UUID`, required 아님, "미사용 시 null") 추가, 도구 설명에 stop 사용법·"새 명령이 아님·점유 중에도 동작·결과를 기다림" 추가. `terminalTimeoutMs`: `stop`이 비어 있지 않은 문자열이면 `STOP_RESULT_TIMEOUT_MS=45_000`(기존 `command: null` 10 s, 명령 실행 150 s 유지).
2. Manager 도구 `stop_command`(`{command_id: uuid, reason: 1..500}`, strict, 둘 다 required)를 `MANAGER_TOOLS`·`BridgeTool`·`BRIDGE_TOOL_NAMES`에 추가하고 도구별 결과 timeout을 45 s로 한다(다른 Manager 도구는 10 s 유지). Worker는 `stop_command`를, Manager는 `terminal`을 갖지 않는다. subagent는 기존처럼 거절된다.
3. `to_worker` 도구 설명에 "cancel은 명령을 멈추지 않는다, 멈추려면 `stop_command`"를 더한다.
4. model-facing skill 문서(영문): `omp_bridge/skills/to-manager/references/terminal.md`(`stop`, `stopping`, `stopped_by`, 명령 id 얻는 곳), `to-worker` 관련 reference와 `workbench-recovery`(`stop_command`, 취소 ≠ 중지, `host_commands`).

## 수락 기준

- CS-AC-03(도구 계약 부분): Worker의 stop 호출이 올바른 frame으로 전달되고 `exited`/`stopping` 결과가 그대로 반환되며 stop 대기가 기존 120 s·10 s timeout에 잘리지 않는다.
- CS-AC-11(도구 계약 부분): Manager `stop_command`가 strict schema로 등록되고 올바른 frame과 timeout으로 전달된다.

## 계약과 맥락

- 기존 관례: strict 도구는 optional 필드를 nullable로 받고 backend가 빈 값을 "미사용"으로 본다(`bridge.ts` 상단 주석). `terminal` 결과의 `terminal_wait_abandoned` 동작은 stop 호출에도 그대로 적용되지만 episode는 계속된다(backend 책임).
- 인자·결과 이름은 SPEC가 정본이다. backend ticket(CS-02, CS-05) 결과와 이름이 어긋나면 이 ticket을 임의로 맞추지 말고 `needs_reroute`.

## 검증

Seam S4(fake backend peer 실제 Unix socket, `node --test`; 기존 `tests/bridge/bridge_terminal_independent_p27cd68.test.ts` 패턴). 독립 기대값은 SPEC의 인자/timeout 계약이며 `bridge.ts` 상수에서 가져오지 않는다. 문서는 TDD 예외(정적 확인).

RED→GREEN 순서:
1. Worker `terminal` schema에 `stop`이 있고 required가 아니며, `{command:"x"}` 호출은 기존처럼 변경 없이 전달된다.
2. `terminalTimeoutMs({command:null, stop:"<uuid>"})==45_000`, `{command:null, stop:null}`==10_000, `{command:"x"}`==150_000.
3. `stop` 호출이 `{tool:"terminal", args:{command:null, stop:id}}` frame으로 나가고 fake peer의 `exited`/`stopping` 응답이 그대로 반환된다.
4. Manager에 `stop_command`가 strict schema로 등록, Worker에는 없음, 인자 검증, 45 s timeout, 다른 Manager 도구 timeout 10 s 유지, subagent 거절.
5. 안내 문서(정적): `terminal.md`·`to-worker`·`workbench-recovery`에 필수 문구, 도구 설명과 schema 일치.
