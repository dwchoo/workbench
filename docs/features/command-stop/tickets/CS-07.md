# CS-07: 사용자 단독 Ctrl+C의 foreground 직접 전달

명세: [../SPEC.md](../SPEC.md) s1. Scheduling·의존성·resource·write scope·gate supplier: [../PLAN.json](../PLAN.json)의 CS-07. 상태·실제 assignment는 Root 운영 기록에서만 관리한다.

## 제공할 동작

Workbench 실행 명령(Worker `terminal` 또는 Manager 실험)이 host terminal의 검증된 foreground일 때, 사용자의 단독 `\x03`(입력이 한 바이트뿐인 `input` 메시지)을 `prefix t,c` 인수 없이, 입력 owner가 `manager`이거나 인수·handoff 진행 중이어도 그 명령에 전달한다. 입력 owner·`takeover_requested`는 바뀌지 않는다. 다른 키·paste·`\x03`이 섞인 입력, 그리고 foreground가 Workbench 실행 명령이 아닌 경우는 현행 규칙 그대로다. 전달 사실이 요청자 `user`로 감사 기록에 남는다.

## 수락 기준

- CS-AC-16: 위 전달, 명령은 보통의 SIGINT 종료(exit 130), 입력 owner 불변, 감사 기록(요청자 `user`, 전달 사실).
- CS-AC-17: `\x03` 외 키·paste·혼합 입력은 현행 규칙(`INPUT_OWNER_MANAGER` 등)으로 거절되고 일부 바이트만 전달되지 않는다. 사용자 소유 prompt/job, 불명 상태에서는 예외가 적용되지 않는다.
- CS-AC-20(부분): `command_interrupt` 레코드(요청자, command_id, 검증된 pid·start_ticks·process_group, `delivered`).

## 계약과 맥락

- SPEC "사용자 Ctrl+C". `PersistentShell.interrupt_run()`은 lifecycle과 `/proc`를 쓰기 직전에 재검증하고(CS-01의 `run_identity` 사용) 경계 `observe_*_bytes`를 부르지 않는다. 현행 `_current_foreground_child_group`은 `owner == "user"`를 요구하므로 owner를 무시하는 변형을 둔다(기존 함수 의미는 유지).
- `ShellPane.admit(data, kind="input")`: 정확히 `b"\x03"`이고 `kind=="input"`이고 `interrupt_run()`이 대상을 검증했을 때만 예외. `Backend.admit(pane_id, data, kind)`가 `kind`를 전달한다(OMP pane은 `kind`를 무시).
- `ShellPane.interrupt_listener`(Backend가 설정)가 `request_id`·검증된 신원을 받고 Backend가 request→command_id를 등록부(터미널은 `request_id==command_id`, 실험은 등록된 `request_id`)로 풀어 journal에 `command_interrupt`를 남긴다. 등록부 해석이 안 되면 `command_id: null`로 남기되 전달은 막지 않는다.
- 위험 지점: 확정된 인수 상태(`confirmed_target`)에서는 기존 `send_confirmed_foreground`가 `\x03`을 이미 전달한다. 이 ticket은 단독 `\x03`을 새 경로로 통일한다(감사 일관성). 기존 테스트가 그 경로의 `dirty`/`input_sequence` 부수효과를 단언하면 `needs_oracle`로 반환한다(조용히 약화 금지).
- 기술 보완: PTY 바이트 쓰기이므로 tty가 ISIG 꺼짐이면 SIGINT가 되지 않는다(사용자가 한계로 수락, SPEC 확정된 결정 3).

## 검증

Seam S5(실제 `PersistentShell`+`ShellPane.admit`). 독립 기대값: 테스트가 띄운 `sleep` 명령의 `child_group`(테스트가 `/proc`/`tcgetpgrp`로 읽음), 종료 코드 130, 입력 owner·takeover 필드의 사전/사후 비교. 기존 `tests/terminal/test_manual_input_*` 패턴 재사용.

RED→GREEN 순서:
1. owner `manager`, 실험/terminal 형태의 managed `sleep 30` 실행 중 `admit(b"\x03")` → `None`, 명령 exit 130, owner 불변.
2. 인수 요청(`takeover_requested`)만 있고 미확인인 중간 상태에서도 전달되고 owner·`takeover_requested` 불변.
3. 거절: `b"a"`, `b"\x03a"`, `b"a\x03"`, paste kind의 `b"\x03"`은 현행 사유로 거절되고 명령은 계속 실행. 일부 바이트 전달 없음.
4. foreground가 사용자 소유 프로그램/prompt이면 예외 없이 현행 규칙(기존 테스트 기대값 유지).
5. main 종료로 foreground가 shell로 돌아온 뒤 `\x03`은 전달되지 않고 현행 규칙.
6. 감사: listener 호출·`command_interrupt` 레코드 필드(요청자 `user`, 신원, `delivered`), 거절 입력은 기록 없음.

작성 범위: `src/workbench/terminal/shell_persistent/adapter.py`, `src/workbench/backend/panes.py`, `src/workbench/backend/service.py`(`admit` 시그니처, listener 연결, journal), `tests/terminal/test_command_interrupt.py`. `*_independent*` 제외.

명령: `env PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src .venv/bin/python -m unittest discover -s tests/terminal -p 'test_command_interrupt*.py'`; 회귀 `... -s tests/terminal -p 'test_manual_input*.py'`, `-p 'test_cw18_host_shell*.py'`, `-p 'test_persistent_shell*.py'`, `... -s tests/backend -p 'test_panes.py'`, `-p 'test_live_input_independent.py'`.

프로세스·신호·입력 경계 작업이므로 독립 `test_designer` 검증 필수. PLAN gate `CS-G07`(runtime). UI 키 입력 경로(실제 키보드→frame)는 이 seam이 잡지 못하며 CS-10에서 `input` frame 수준으로 확인한다.

## 범위 밖과 중단 조건

`ui/product/*`, 인수 규칙(`prefix t,c`), lifecycle 상태기계는 바꾸지 않는다. 다른 키를 허용하는 변경은 금지. `observe_*_bytes` 계약 변경이 필요해 보이면 멈추고 `needs_reroute`.

## 출력

후보 id, 변경 경로, 정확한 명령·결과, behavior별 RED/GREEN, 기존 테스트 영향 목록(특히 확정된 인수 상태), 한계, 소유 process 종료 확인.
