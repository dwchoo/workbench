# CS-10: 최종 통합·실제 시간·감사·독립 검증

명세: [../SPEC.md](../SPEC.md) s1. Scheduling·의존성·resource·write scope·gate supplier: [../PLAN.json](../PLAN.json)의 CS-10. 상태·실제 assignment는 Root 운영 기록에서만 관리한다.

## 제공할 동작

CS-01~09가 통합된 후보에서 기능 전체를 교차 확인한다. 새 제품 동작은 만들지 않고, 통합 중 발견된 결함은 해당 ticket 범위의 수정 작업으로 되돌린다. 문서(core 조항 주석)는 SPEC 표로 갈음하며 core 문서는 수정하지 않는다.

## 수락 기준

CS-AC-01~23 전부를 구현·현재 검증 증거로 연결한다(PLAN `acceptance_trace`). 추가 최종 확인:

1. 실제 기본 정책(10/5/5 s)으로 SIGINT·SIGTERM 무시 명령 stop의 단계 간격과 총 시간(약 20 s)을 측정한다(CS-AC-03, 04, 05, 09, 10). `tests/integration/live_command_stop.py`.
2. bridge↔backend 교차 검증: CS-06이 내보낸 schema가 허용하는 인자 frame을 `Backend._tool_request`에 그대로 넣어 `terminal.stop`·`stop_command`가 처리되고, 기존 `{command}`-only 호출이 계속 동작한다(CS-AC-03, 11).
3. 감사 완결성(CS-AC-20): 하나의 결합 시나리오(Worker stop, Manager stop, 거절, unknown→정정, Ctrl+C, 실험 stopped)를 실행한 뒤 journal에서 요청자, 대상(command_id·검증 pid·start_ticks), 신호와 시각, 종료 상태, 잔존 확인, 거절·unknown 이유, 정정 이력, 실험 `stopped_by`가 모두 조회되고 환경 변수 값·auth·argv가 없음을 확인.
4. `input` frame 수준 Ctrl+C: `Backend.admit(host_shell, b"\x03", "input")`로 UI 경로 직전까지 확인(CS-AC-16, 17). 실제 키보드 경로는 UI 변경이 없어 범위 밖이다.
5. 실제 OMP schema 수용(CS-AC-03, 11, `runtime`): 설치된 OMP(`omp`, 기대 18.6.1)를 가짜 provider(`tests/backend/live_omp_tools_independent_p27cd68.py` 방식)로 띄워 Worker 요청에 `terminal`의 `stop`, Manager 요청에 `stop_command`가 포함되는지 captured body로 확인한다. OMP 바이너리/환경이 없으면 `not_run`으로 보고하고 다른 증거로 대체 주장하지 않는다(**live evidence pending 후보**).
6. 넓은 관련 회귀를 최종 후보에서 한 번 실행: `tests/backend`(모듈 범위별), `tests/terminal`, `tests/workflow`, `tests/tasks`, `tests/contracts`, `tests/recovery_boot`, `node --test tests/bridge/*.test.ts`. 소요가 큰 live harness는 변경 관련 모듈만, 전체는 디렉터리별로 따로 실행한다(`-t .` 금지).

## 계약과 맥락

SPEC 전체. 증거 level은 PLAN `gate_items`(`CS-G10`~`CS-G13`)를 따른다. 최종 검토: Standards·Spec 두 fresh reviewer가 같은 frozen 후보·전체 diff(새 파일 포함)를 보고, 신호·신원·입력 경계가 security trigger이므로 별도 `review_kind: security` reviewer와 diff secret scan을 둔다(위협: PID 재사용/TOCTOU, uid·session 경계, Manager `reason`의 주입·비밀, 감사 기록 누출, 이전 backend 대상 오조준, 입력 우회 범위). 모델 security 검토는 가설 수준 증거이며 증명으로 쓰지 않는다. scope audit: 변경이 PLAN 승인 범위 안인지, `ui/product/*`·core 문서·SQLite schema가 변하지 않았는지 확인.

## 검증

실제 PTY·실제 프로세스·실제 시간. 독립 `test_designer`가 요구에서 도출한 최종 시나리오를 먼저 확인한다. 실패는 원인(코드·테스트·환경·계약)을 분류해 해당 ticket 범위의 수정 작업으로 돌리고 Root가 판정한다. 통과한 동일 후보·환경의 근거를 반복 실행하지 않는다. 최종 명령 목록(전부 repo 루트, 공통 접두사 `env PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src .venv/bin/python`): SPEC "테스트 결정"의 명령 + `... -m unittest tests.integration.live_command_stop`(필요 시 환경 변수로 활성화). `tests/gates`는 쓰지 않는다. 작성 범위: `tests/integration/live_command_stop.py`(통합 시나리오), 이름에 `_independent`가 있는 파일은 test_designer 소유, 검증 기록 `docs/features/command-stop/VERIFICATION.md`.

PLAN gate: `CS-G10`(runtime, 실제 시간), `CS-G11`(runtime, 감사), `CS-G12`(runtime, 실제 OMP schema, 환경 의존), `CS-G13`(static, review·security·scope·trace).

## 범위 밖과 중단 조건

새 기능, core 문서 수정, 운영 배포, commit/push, Docker, 새 도구 설치, 유료 provider는 하지 않는다. 필수 runtime(OMP)이 없으면 해당 gate는 `not_run`이고 성공으로 간주하지 않는다. 테스트가 만든 process·temp dir·checkpoint는 정리하고 `.workflow` 용량을 확인한다.

## 출력

후보 id, 각 gate의 명령·exit code·개수·시간, 감사 완결성 표, 실측 단계 간격, 미실행(`not_run`) 항목과 이유, review/security 결과 요약, 소유 process 종료 확인.
