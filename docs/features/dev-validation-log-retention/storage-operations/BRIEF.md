# 로그 용량 관리 운영 마무리 — 후속 요구사항

Revision: b1, 2026-10-18. 상태: 사용자 합의 방향을 정리한 계획 입력. 후속 SPEC·PLAN bundle은 검토 전 초안이다.

## 출처와 권한

원 입력은 [상위 BRIEF](../BRIEF.md)의 r0.9 및 LG-D15~33 후속 합의다. 용어는
[CONTEXT](../../../../CONTEXT.md)의 raw log rotation·중요 로그·활성 DB·보존 DB를 그대로 쓴다.
상위 BRIEF/SPEC/PLAN, DVL-01~14와 기존 후속 ticket, 승인·완료·실패 기록을 수정하거나 대체하지 않는다.

이번 대화의 직접 근거는 다음과 같다. 발화 ID가 별도 제공되지 않아 날짜·원문·대상으로 식별한다.

- U-OPS-01: 사용자가 원본 출력의 디스크 누적을 우려하고 추천안을 요청했다.
- U-OPS-02: 원본 약 500MB 공용 순환, 기존 중요 로그 정책 유지, 기존 로그 선택 정리 제안 뒤
  사용자: **“좋아 그렇게 하자. 개발 계획을 세워봐.”** 방향 채택과 계획 작성 요청이다.
- U-OPS-03: 이번 사용자 명령 **`$to-tickets docs/features/dev-validation-log-retention/BRIEF.md`**.
  후속 SPEC·ticket 작성 권한이며 구현·모델 실행·실제 삭제·활성화·commit 권한이 아니다.

## 목표와 범위

사용자가 원본 출력과 중요한 작업 기록의 보관 차이를 이해하고, 실제 사용량·자동 관리 범위·
수동 정리 대상을 확인할 수 있게 한다. 기존 엔진을 재구현하지 않고 현황 조사, 기존 CLI 표시의
확인된 공백 보완, 관련 실행 경로 검증, 적용·선택 정리 안내를 작은 후속 단위로 묶는다.

1. 원본은 기존 `100_000_000 bytes × 5개` 공용 순환 정책을 사용한다. 실험과 Worker terminal이
   같은 예산을 공유한다. 500MB는 segment 파일 예산이지 control metadata·legacy·중요 DB를
   포함한 프로젝트 전체 디스크 상한이 아니다. 최초 운영 활성화는 기존 gate와 별도 사용자 결정이 필요하다.
2. 활성 중요 로그 DB의 250MB 논리 용량 목표·보관 종결 후 120일·용량 압박 정리를 유지한다.
   DB/WAL/SHM의 물리 크기와 구분하고, 시작·최신 누적 요약·실행 근거의 기존 보호를 유지한다.
3. 보존 DB는 자동 삭제하지 않는다. 개수·물리 용량·정리 필요 상태를 표시하고 기존 UUID 선택
   삭제 절차를 안내한다. 활성 DB·미확인 orphan을 보존 DB처럼 지워서는 안 된다.
4. 기존 legacy 파일은 신규 정책으로 이관하거나 소급 삭제하지 않는다. 먼저 크기·작업 연결·
   종료 여부를 조사한다. 전용 legacy 삭제 API가 없으므로 이번에는 후보 보고와 수동 절차만 준비한다.
   실제 정리 명령 실행은 선택 대상에 대한 별도 승인 뒤의 운영 작업이다.
5. 원본 순환을 요약 성공에 종속시키지 않는다. 요약 실패는 최소 사유와 마지막 정상 기록을 남기고,
   raw 누락은 정확한 source/range로 표시한다. sent/unknown 입력 자동 재전송은 금지한다.

## 비목표와 유지 조건

- 전체 data dir의 절대 용량 상한, 보존 DB 자동 삭제, 새로운 legacy 삭제 명령·백필·마이그레이션,
  자동 중요도 agent, 품질 평가/자동 교정, 새 저장 엔진·DB schema·잠금·queue·상주 서비스는 추가하지 않는다.
- 요약은 기존 Worker.default·DB-only tool·host 고정 writer·작업 귀속·no replay 경계를 유지한다.
  모델·예산·fallback 정책을 바꾸거나 실제 유료 요약 시험을 반복하지 않는다.
- C2 hold, 실제 raw 삭제 비활성, 기존 Q01 8개 및 상위 28 AC/46 gate ID·증거 수준을 유지한다.
  개발 후속 완료와 운영 활성화 가능은 구분한다. 활성화 차단은 우회하지 않는다.
- 제품/시험 구현은 후속 bundle 승인 후다. 이 계획 턴에는 runtime·테스트 실행을 하지 않는다.

## 수락 예시

세부 ID와 관측 방법은 [SPEC](SPEC.md), 실행 소유권은 [PLAN](PLAN.json)을 따른다.

- legacy 400MiB와 segmented 200MB가 있으면 둘을 따로 표시한다. 전체가 500MB 이하라고 말하지 않는다.
- 명령별 legacy 64MiB 한도와 실험 legacy 합계 512MiB 한도를 구분한다. terminal 파일 합계에
  실험의 512MiB 한도가 적용된다고 안내하지 않는다.
- 보존 DB가 2개면 활성 DB 목표 250MB와 별도로 전체 DB 개수·물리 용량·수동 정리 필요를 보여준다.
- 확인할 수 없는 사용량은 unknown/partial로 표시한다. missing store와 읽기 실패를 같은 0으로 표시하지 않는다.
- 임시 mixed-producer 시나리오에서 원본이 교체돼도 작업 결과·필수 근거·기존 정상 요약이 남고,
  삭제된 원본은 읽을 수 있다고 표시하지 않는다. 모델 성공을 기다리며 무한 보관하지 않는다.
- 조회·문서 확인만으로 verify, 모델 호출, 활성화, DB 유지보수·삭제가 시작되지 않는다.

## 현재 사실과 미확인

계획 당시 source 조사에서는 기존 `raw-status`의 비JSON 출력도 JSON 그대로였고, 중요 로그 status의
사람용 출력은 합계/active UUID 중심이었다. 기존 JSON·status port를 재사용해 설명을 보완할 여지가 있다.
순환 엔진·유지보수·삭제 보호와 관련 시험은 이미 존재한다. 존재는 현재 통과를 뜻하지 않는다.

이전 기능 완료는 `c15ae38b6ada6f2ae3bb0ca706ff90b564072fd7` 및 상위 최종 기록의 범위다.
현재 CLI down alias·렌더 색상 cache와 사용자 workflow 변경이 dirty이므로 새 candidate로 다시 관측해야 한다.
현 데모의 용량·현재 product record의 최초 활성화 적합성은 이번 계획에서 조회/실행하지 않아 미확인이다.
기존 goal은 complete이며 재개하지 않는다. 이번 후속은 별도 구현 단위다.

이번 방향에는 추가 제품 결정이 없다. 운영 대상과 삭제 대상 선택·활성화 승인은 실제 적용 전 남는다.
