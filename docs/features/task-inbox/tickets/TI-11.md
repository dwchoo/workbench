# TI-11: Manager `workbench_inbox`·`to_worker.request_id` link·Task 동기화·close·skill

명세: [../SPEC.md](../SPEC.md) s1. 의존성·자원: SPEC "Ticket 그래프"의 TI-11(선행 TI-10). 상태·실제 assignment는 orchestrator 운영 기록에서만 관리한다.
권장 executor: Opus(`model: "opus"`). 승인 명세 연결과 worker 전달 순서(ADR-0004, D-35)의 핵심이다.

## 제공할 동작

- `bridge.ts`: manager 전용 `workbench_inbox` 도구(SPEC "Manager 도구" 인자, strict, essential) 등록. `to_worker` schema에 `request_id`(nullable canonical UUID)와 설명(검토한 요청을 Task로 보낼 때 붙임). Tool 설명에 결과의 `inbox` 필드.
- Backend `_tool_request`: `workbench_inbox` → `inbox_link` client → hub_v1 `inbox_list`/`inbox_show`/`inbox_review`. 결과 mapping(`inbox_unavailable`, `unknown`).
- `flow.py`·`flow_tasks.py`: `_TO_WORKER_KEYS`에 `request_id`. `request_id`가 있으면 SPEC의 link check → Task 생성/명세 revision(명세 문서 `inbox_request_id`) → link commit → 성공일 때만 `_delegate`. 거절은 `inbox_link_refused`(Task 미생성 또는 전달 없이 `closed_reason: inbox_link_refused`), 불명은 `inbox_link_unconfirmed`로 닫고 `unknown`. 결과에 `inbox:{request_id, state}`.
- Hub `InboxService`: `inbox_review`의 `begin_review`·`ask`(REVIEWING·RUNNING → NEEDS_INFO, `question` 댓글)·`comment`(`progress`)·`reject`(CLOSED(rejected), `decision` 댓글)·`close`(READY·RUNNING → CLOSED(success/failed), summary 필수 ≤ 16 KiB). `inbox_link_check`(REVIEWING·NEEDS_INFO만, token 30 s, 그 요청의 이후 commit이 token 무효화)·`inbox_link_commit`(task_id·spec_revision·READY/RUNNING, links 이력).
- Hub Task 동기화(`dispatch.py`): SPEC "Task 동기화" mapping, `task_view` 갱신, `inbox_link_unconfirmed` → READY → REVIEWING(void), 그 밖의 closed → `linked_task_closed` 통지 1회.
- `omp_bridge/skills/workbench-inbox/SKILL.md`(English) + manager role skill allowlist. To-worker skill에 `request_id` 한 줄.

## 수락 기준

- P2-AC-25: fake OMP `tool workbench_inbox {"action":"ask",…}` → NEEDS_INFO·질문 댓글(웹·MCP에 보임). Owner(웹)·board_agent key·원 requester key 각각의 답 → REVIEWING·재통지(자동). `reject` → CLOSED(rejected).
- P2-AC-26: `tool to_worker {… "request_id": R}` → 요청에 task_id·spec_revision, READY → Task 시작 관측 뒤 RUNNING. Task가 `finished`여도 manager `close` 전에는 CLOSED 아님(P2-AC-09). `close success` → CLOSED(success)·summary.
- P2-AC-27: RUNNING 요청에 `ask` → NEEDS_INFO(link 유지) → 답 → REVIEWING → 후속 `to_worker`(task_id + request_id) → 다시 연결.
- P2-AC-28: 소유자·Board agent·외부 key 출처 요청 세 개가 같은 경로로 dispatched(`scope_approved`+`proceed` 기록, 소유자 승인 단계 없음).
- P2-AC-43·TI-T09: link check 뒤 commit 전에 취소가 commit되면 link commit 거절 → worker에게 TASK frame 없음(`$FAKE_FRAMES`·mailbox), Task는 전달 없이 닫힘. Hub 정지 상태에서 `to_worker`+request_id → Task 미생성·전달 없음. Commit 응답 불명(테스트가 Hub 응답을 끊음) → 전달 없음, Hub 쪽 READY면 동기화가 REVIEWING으로 되돌림.
- P2-AC-06: `workbench_inbox list/show`는 모델·worker frame을 만들지 않음.
- P2-AC-33(일부)·불변식 7: owner·editor·requester principal의 link·READY·RUNNING·close 시도는 거절(TI-04 matrix 재확인을 hub_v1 경로로).

## 계약과 맥락

SPEC "Manager 도구", "Task 동기화", "취소"의 D-35 경합. C-D66 `_delegate`(`flow_tasks.py:956-986`), `_to_worker`(`:988` 이후), `flow.py` 인자 검증(`:378`, `:503`), `bridge.ts` `HANDOFF_TOOLS`·`MANAGER_TOOLS`·등록(`:1205` 이후), launcher `role_skill_allowlist`.

## 검증

Seam T6(실제 backend + fake OMP + 실제 Hub). 독립 기대값: `$FAKE_FRAMES`(worker에 간 TASK), `tasks.sqlite3`(stdlib 읽기: task·decision 행), inbox 파일, SPEC 전이표.

Behavior 순서: 도구 등록(bridge 정적 + fake OMP 호출 경로) → list/show → begin_review → ask/답변/재통지 → reject → link check 거절(Task 미생성) → link 성공·READY → 시작 → RUNNING → close·summary → 완료 판단 전 미종료 → RUNNING ask(P2-AC-27) → 경합(취소 먼저) → Hub 없음 → commit 불명·void → linked_task_closed → 세 출처.
