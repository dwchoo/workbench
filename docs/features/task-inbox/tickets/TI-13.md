# TI-13: 취소 경로(사용자 Task 취소·사용자 stop·READY/RUNNING·경합)

명세: [../SPEC.md](../SPEC.md) s1. 의존성·자원: SPEC "Ticket 그래프"의 TI-13(선행 TI-05, TI-06, TI-11). 상태·실제 assignment는 orchestrator 운영 기록에서만 관리한다.
권장 executor: Opus(`model: "opus"`). 실행 중 명령 종료와 Task 상태 전이, 경합 순서다.

## 제공할 동작

- Backend `TaskFlow.cancel_by_user(task_id, reason, expect)`: 현재 Task 상태·실행 중 Workbench 명령이 `expect`와 다르면 `task_changed`. 같으면 기존 `_cancel` 절차(withdraw, host run이면 `cancelling` + host exit 대기, 아니면 `_finish_cancel`)를 `by: "user"`로 실행하고 `closed_reason`이 사용자 취소임을 구분할 수 있게 기록. 그 Task의 실행 중 명령이 있으면 기존 사용자 stop(`service.py`의 CS-O10 경로, `requested_by: user`)을 background로 시작. 결과 `{cancel, stop}`. Manager에게 `inbox_request`(event `cancelled`) 통지.
- ui_v1 `cancel_task` controller 구현(TI-09 자리 채움).
- Hub `InboxService` cancel port 실구현: READY(확인 없이)·RUNNING(웹 확인 page token / MCP 2단계 token) → `cancel_state=requested` commit → backend `cancel_task` → 결과 반영(`stop_requested` 등, system 댓글). Backend 꺼짐이면 commit 전 `backend_not_running`. Backend `task_changed`면 `cancel_state` 원복·`token_mismatch` 성격의 거절. Task 동기화가 사용자 취소로 닫힌 Task를 보면 CLOSED(cancelled). 명령 stop `unknown`은 system 댓글, 성공 표시 없음.
- 취소 주체 제한(owner·board_agent/editor·원 requester)을 Hub 경로 끝까지.

## 수락 기준

- P2-AC-30: 실행 전 취소 즉시 CLOSED(cancelled). RUNNING(fake OMP worker의 terminal 명령 실행 중) → 웹 확인 page → 확인 → 명령에 SIGINT부터 stop(`requested_by: user`, command stop 기록) + Task 취소 → 명령 종료·Task closed 관측 뒤에야 CLOSED(cancelled). 수락 직후 응답·page는 "취소 요청됨"이지 "취소됨"이 아님. 다른 requester key의 취소 거절.
- P2-AC-41(실물): MCP `inbox_cancel` 2단계, 그 사이 Task가 다른 상태로 바뀌면(명령 끝남) 확인 거절·아무것도 멈추지 않음(명령 stop 기록 없음).
- P2-AC-43: link check와 commit 사이 취소 → CLOSED(cancelled), worker 전달 없음. Link commit 뒤 취소 → READY 취소 경로로 Task 취소(전달 전이면 withdraw로 worker frame 없음).
- READY 취소(명령 없음)는 확인 없이 진행, Task가 전달 전이면 worker에 아무것도 가지 않음.
- Backend 꺼짐 상태 RUNNING 취소 → `backend_not_running`, 요청 불변.

## 계약과 맥락

SPEC "취소", "Task 동기화". 명령 stop BRIEF CS-D03, CS-O10(`service.py:1645` 사용자 stop, `ui_server.py` `stop_command`), `flow_tasks.py` `_cancel`(`:1252`)·`_finish_cancel`·withdraw, D-20·D-33·D-35.

## 검증

Seam T6(실제 backend + fake OMP + 실제 Hub, worker의 terminal 명령은 `sleep` 계열 host 명령) + T7(`cancel_task` 허용·expect 검사). 독립 기대값: `/proc`의 명령 pid 소멸, command stop 기록(`requested_by`), `tasks.sqlite3` 결정 행, `$FAKE_FRAMES`, inbox 파일.

Behavior 순서: `cancel_by_user` expect 불일치 거절 → 명령 없는 Task 취소 → 실행 중 명령 Task 취소(사용자 stop) → ui_v1 `cancel_task` → Hub READY 취소 → RUNNING 웹 확인 → MCP 2단계 실물·상태 변경 거절 → 관측 뒤 CLOSED → stop unknown 표시 → backend 꺼짐 거절 → 경합 2종 → 권한.

작성 범위: `src/workbench/backend/{flow_tasks,service,ui_server}.py`, `src/workbench/hub/inbox/{service,dispatch,backend_port}.py`, `src/workbench/hub/web/pages/requests.py`(결과 문구), `tests/hub/test_inbox_flow_cancel.py`, `tests/backend/test_ui_server_inbox.py`(추가).
