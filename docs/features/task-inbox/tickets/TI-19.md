# TI-19: 최종 통합·live·독립 검증·security review·dependency audit

명세: [../SPEC.md](../SPEC.md) s1. 의존성·자원: SPEC "Ticket 그래프"의 TI-19(선행 TI-01~18). 상태·실제 assignment는 orchestrator 운영 기록에서만 관리한다.
권장 executor: Sonnet(`model: "sonnet"`) test_designer/검증. 통합 중 발견된 결함은 해당 ticket 범위의 수정으로 되돌리고 그 ticket의 모델로 고친다.

## 제공할 동작

TI-01~18이 통합된 후보에서 기능 전체를 실제 Hub·backend(fake OMP)·가짜 Board `omp`·loopback HTTP/WS로 교차 확인한다. 새 제품 동작은 만들지 않는다.

## 수락 기준

P2-AC-01~45, TI-T01~T10 전부를 SPEC "수락 기준" 표의 책임 ticket 증거와 이번 통합 증거에 연결한다. 추가 최종 확인(`tests/integration/live_inbox*.py`):
1. 끝에서 끝: 웹 로그인 → 요청 작성(소유자) → 자동 통지 → fake manager `workbench_inbox show`·`to_worker request_id` → worker 실행(host 명령) → RUNNING → 결과 보고 → manager `close success` → 웹·MCP 요약·전체 보기. 같은 흐름을 외부 requester key(MCP)와 Board 시스템 key 출처로 한 번씩(P2-AC-28).
2. Hub 정지 중 core: Task 진행 중 `wb hub stop` → backend·worker·명령 계속, manager `workbench_inbox`는 `inbox_unavailable`, Hub 재시작 뒤 요청·세션 보존(P2-AC-01·23).
3. 프로젝트 꺼짐 접수 → 켜기(웹) → 순서대로 통지(P2-AC-04·23).
4. RUNNING 취소(웹 확인·MCP 2단계) → 명령 stop·Task 취소 → CLOSED(cancelled)(P2-AC-30·41).
5. Board 세트 + `wb update`(update fixture): 확인 목록에 세트, 확인 뒤 세트·Hub 정지, backup에 `inbox.sqlite3`(TI-T07·T08).
6. 단일 writer: 흐름 1~4 동안 backend·Board agent·CLI 프로세스의 `/proc/<pid>/fd`에 `inbox.sqlite3`가 없음(TI-T03). 다른 HOME의 Hub가 같은 프로젝트 inbox에 쓰려 하면 `inbox_busy`.
7. Manager·worker 기존 격리·MCP 누출 검사 통과(P2-AC-33), 기존 manager `to_worker`(request_id 없음)·명령 stop·pause/resume 회귀.
8. 회귀 넓게 한 번(디렉터리별, `-t .` 없음): `tests/hub`, `tests/backend`(모듈 범위별), `tests/backend/installation`, `tests/backend/maintenance`, `tests/ui`, `tests/recovery_boot`, `tests/contracts`, `tests/bridge`, `tests/tasks`, `node --test tests/hub/js/`. `*_independent*` CLI-spawning 파일의 sandbox 위생(짧은 private XDG_RUNTIME_DIR, `WORKBENCH_HUB_AUTOSTART=0`) 확인, 끝난 뒤 남은 Hub·backend·PTY 프로세스 없음(`/proc`).
9. 정적: wheel에 web 자산·license, 제공 page·JS 외부 URL 없음, `mcp` SDK import 없음, `pyproject.toml` pin(P2-AC-37).
10. `pending`(이 host에서 `not_run`): SPEC "대상 host 확인 항목" 1~7. 다른 증거로 대체 주장하지 않는다.
11. Acceptance trace 표를 `docs/features/task-inbox/VERIFICATION.md`에 남긴다.

## 계약과 맥락

SPEC 전체. 최종 검토: Standards·Spec 두 fresh reviewer가 같은 frozen 후보·전체 diff(새 파일 포함)를 본다. Security trigger(LAN listener, 인증·세션·CSRF, API key, MCP, 웹 terminal, 비attach 제어 확장, 산출물 경로, 새 의존성)이므로 별도 security reviewer와 diff secret scan을 둔다. 위협 목록: 비밀번호 없음·손상 상태 listener 개방, 세션 고정·탈취(cookie flag), CSRF·DNS rebinding(Host/Origin), 로그인 brute force(지연 우회), key 원문 누출(log·감사·응답), requester의 남 요청 열람·존재 추론, editor·key로 승인·terminal·제어 도달, MCP cookie 경유 CSRF, WS 인수 우회·이전 epoch 입력, 산출물 경로 탈출·TOCTOU, Board agent의 추가 MCP·설정 노출, 시스템 key 재사용, backend principal 위조, ui_v1 비attach 확장 오용, 요청 본문을 통한 manager prompt injection(소유자 신뢰 모델 안에서의 위험 기록). Dependency audit: `DEPENDENCY-AUDIT.md` 갱신(SPEC 열린 결정 2의 결정대로). Scope audit: `tasks.sqlite3`·`backend.json`·설치 manifest 구조 불변, `.wb`에는 `inbox.sqlite3`·`inbox.lock`만 추가.

## 검증

실제 프로세스·loopback·fake OMP·가짜 Board `omp`. 독립 test_designer가 요구에서 도출한 최종 시나리오를 먼저 확인한다. 실패는 원인(코드·테스트·환경·계약)을 분류해 해당 ticket 수정으로 돌리고 orchestrator가 판정한다. 같은 후보·환경에서 통과한 근거를 반복 실행하지 않는다. 새 격리 실행 전후 `du -sh .workflow graphify-out .worktrees`.

명령(repo 루트, 접두사 `python3 tools/shm_tests.py -- env PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src .venv/bin/python`): SPEC "테스트 결정"의 명령 전부 + `… -m unittest discover -s tests/integration -p 'live_inbox*.py'`. `tests/gates`는 쓰지 않는다.

작성 범위: `tests/integration/live_inbox*.py`, `*_independent*` 파일(test_designer 소유), `docs/features/task-inbox/VERIFICATION.md`, `docs/features/task-inbox/DEPENDENCY-AUDIT.md`(갱신).

## 범위 밖과 중단 조건

새 기능, 운영 배포, commit/push, Docker, 새 도구 설치(열린 결정 2가 허용한 것 제외), 실제 사용자 systemd·`~/.omp` 조작, 실제 모델·유료 provider. 필수 runtime이 없으면 `not_run`이고 성공으로 보지 않는다. 테스트가 만든 process·temp dir을 정리하고 `.workflow` 용량을 확인한다.
