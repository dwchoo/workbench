# HB-04: registry·자동 등록·`wb init`·`wb hub add/remove`

명세: [../SPEC.md](../SPEC.md) s1. 의존성·자원: SPEC "Ticket 그래프"의 HB-04. 상태·실제 assignment는 orchestrator 운영 기록에서만 관리한다.
권장 executor: Sonnet(`model: "sonnet"`). 기존 파일 원자 쓰기·lock 패턴을 따르는 CLI 작업이다.

## 제공할 동작

`registry.json`의 읽기·쓰기·`ensure`·`remove`. `wb start`(시작·이미 실행 중 연결)와 새 `wb init [PATH]`가 자동 등록하고, `wb hub add/remove <PATH>`가 수동 관리한다. 등록 해제는 `.wb/`를 건드리지 않는다.

## 수락 기준

- HB-AC-05: `wb init`(PTY에서 `y`) → `.wb` 생성 + 등록(`source:"init"`), backend 미시작. 이미 초기화된 폴더의 `wb start --no-attach`(이 ticket에서는 시작 요건 실패 경로가 아니라 계약 fixture backend가 이미 실행 중인 경로로 확인) → 등록(`source:"start"`). 기능 도입 전 `.wb`(registry 없음)도 첫 시작에서 등록된다. `wb hub add <root>` → 등록(`source:"add"`).
- HB-AC-07: `remove` 뒤 `.wb/` 아래 모든 파일 bytes·mode 불변. 재등록하면 같은 `project_id`.
- HB-AC-14: 같은 root 두 번 `add` → 항목 하나(멱등). 다른 root의 같은 `project_id`는 거절. 하위 폴더 `add` → exit 1 + 그 root 안내. 하위 폴더 `wb init` → exit 1, `.wb` 미생성.
- HB-AC-17: 미초기화 경로 `add` → exit 1, `wb init <PATH>` 안내, `.wb` 미생성. 켜진 프로젝트(계약 fixture backend가 lock을 잡은 상태)의 `remove` → `먼저 끄세요`, exit 1, `registry.json` bytes 불변.
- HB-T05: 손상 `registry.json`(JSON 오류·schema 오류·0644 mode)에서 `add`는 exit 1, 파일 bytes 불변. 자동 등록은 stderr 경고 한 줄, 명령 계속. 4개 프로세스가 동시에 서로 다른 root를 `add`해도 4개 모두 남는다.
- `wb init` TTY 아님 → exit 2, `.wb` 미생성. 거절 답 → `.wb` 미생성.
- 같은 root가 다른 id로 등록된 상태의 자동 등록은 덮어쓰지 않고 경고.

## 계약과 맥락

SPEC "Registry 계약", "CLI 계약"의 `wb init`·`add`·`remove`. `initialize_project`·`resolve_project_context`·`read_project_marker`(`backend/project.py`), `write_private_json`. `remove`의 상태 판정은 `inspect_backend`로 한다: `running`·`starting`·`BackendIdentityError`면 거절(SPEC 표의 `on`·`starting`·`closing`·`unknown`). `_cmd_start`의 성공 경로(시작·이미 실행 중) 끝에서 `ensure`를 부르고 실패는 경고만(시작을 막지 않는다). `--data-dir`/`WORKBENCH_DATA_DIR`가 `.wb` 형태가 아니면 등록하지 않는다.

## 검증

Seam S3(registry API + bytes, 다중 프로세스) + S1(CLI). 켜진 상태는 이 ticket이 만드는 계약 fixture backend `tests/hub/fixtures/contract_backend.py`로 만든다(`tests/backend/installation/test_project_cli.py`의 delayed-backend 참고: `.wb/backend.lock`을 잡고 `backend.json`·`runtime.json`을 쓰고 ui_v1 `snapshot`에 테스트가 준 JSON으로 답한다). HB-05가 지연·잘못된 신원·frame 기록 기능을 더한다. 독립 기대값: 테스트가 만든 경로·marker의 project_id, 파일 bytes·mode·mtime.

Behavior 순서:
1. 빈 상태 `ensure` → 파일 생성(0600), schema.
2. 멱등·유일성(root, project_id).
3. 손상 파일 읽기·쓰기 거절.
4. 동시 쓰기 유실 없음.
5. `wb hub add` 정상/미초기화/하위 폴더/id 충돌.
6. `wb hub remove` 정상(`.wb` 보존)/미등록/켜짐 거절.
7. `wb init` 정상/비TTY/거절/하위 폴더/이미 초기화.
8. `wb start` 자동 등록(이미 실행 중 연결 경로), 손상 registry에서도 start 계속.

작성 범위: `src/workbench/hub/registry.py`, `src/workbench/hub/cli.py`(init/add/remove), `src/workbench/backend/cli.py`(parser `init`·`hub add/remove`, `_cmd_start` 끝), `tests/hub/test_registry.py`, `tests/hub/test_hub_cli_registry.py`, `tests/hub/fixtures/contract_backend.py`.

명령: `python3 tools/shm_tests.py -- env PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src .venv/bin/python -m unittest discover -s tests/hub -p 'test_registry*.py'`, `… -p 'test_hub_cli_registry*.py'`. 회귀: `… discover -s tests/backend/installation -p 'test_project_cli*.py'`, `-p 'test_project_context.py'`.

독립 test_designer 검증 권장(이 ticket은 Sonnet 정형 작업이지만 파일 원자성·경합이 있다). 초점: 동시 쓰기, 손상 파일 비파괴, symlink된 상태 디렉터리·registry 파일 거절, `.wb` 보존의 bytes 수준 확인, 하위 폴더·중첩 판정.
