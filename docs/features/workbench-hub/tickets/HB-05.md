# HB-05: 상태 집계·hub_v1 `list`·`wb hub list`

명세: [../SPEC.md](../SPEC.md) s1. 의존성·자원: SPEC "Ticket 그래프"의 HB-05. 상태·실제 assignment는 orchestrator 운영 기록에서만 관리한다.
권장 executor: Opus(`model: "opus"`). backend 신원 대조와 "관측 실패 ≠ 꺼짐" 불변식이 핵심이다.

## 제공할 동작

Hub가 `list` 요청마다 registry를 다시 읽고 항목별로 `check_entry` → `inspect_backend` → (running이면) attach 없는 ui_v1 `snapshot` + 신원 대조를 병렬로 해서 행을 만든다. `wb hub list [--json]`이 TUI와 같은 열로 보인다. label·서식은 `workbench.hub.presentation` 한 곳이다.

## 수락 기준

- HB-AC-12: 계약 fixture backend가 준 snapshot에서 행의 `task`(status·summary), `command`(`panes.host_shell.command`), `waits`(paused, boot_confirmation_required, manager_editor_not_empty, manager_session_not_connected, metadata_unavailable, model_hold, task_held — SPEC 순서), `last_activity`가 SPEC 표대로 나온다. 텍스트 출력의 열 순서는 이름, 경로, 상태, Task·단계, 명령, 대기 사유, 요청, 마지막 활동.
- HB-AC-12(불명): fixture가 snapshot에 답하지 않음(2 s 초과) → `unknown/timeout`. 신원 불일치 snapshot(다른 pid·data_dir) → `unknown/snapshot_mismatch`. `inspect_backend` 오류(lock은 잡혔는데 `backend.json` 없음 등) → `unknown/identity:<reason>`. 어느 경우에도 `off`가 아니다. 한 행의 timeout이 다른 행 결과를 늦추거나 바꾸지 않는다.
- HB-AC-13: 경로 없음 → `mismatch/root_missing`, `.wb` 없음 → `not_initialized`, marker 손상 → `marker_invalid`, project_id 다름 → `project_id_mismatch`.
- HB-AC-06: registry에 없는 초기화된 `.wb`는 행에 없다(Hub는 디렉터리를 탐색하지 않는다).
- HB-AC-19: 모든 행 `pending_requests: null`, 텍스트·label은 `—`.
- 손상 registry → `list` 결과 `registry.state: "invalid"`, `wb hub list` exit 1.
- `fresh:false` 반복 요청은 2 s 안에 backend에 다시 연결하지 않는다(fixture가 받은 연결 수로 확인). `fresh:true`는 새로 관측.
- 관측 연결은 attach하지 않는다(fixture가 받은 frame에 `attach` 없음, hello client `workbench-hub`).

## 계약과 맥락

SPEC "Hub ↔ backend IPC", "상태 집계", "hub_v1"의 `list`. 신원 대조는 `cli._running_snapshot`(`backend/cli.py:65-85`)의 규칙을 함수로 빼서 공유한다(동작 불변, 기존 호출자 회귀 확인). 관측은 executor thread(최대 8)에서. `observed_at`, 행별 `observed_at`. `wb hub list`는 Hub가 없으면 자동 시작 규칙(HB-02)으로 띄운 뒤 묻는다.

## 검증

Seam S4(계약 fixture backend + `wb hub list --json`, 필요하면 S2로 `list` 직접) + presentation 단위. Fixture는 HB-04가 만든 `tests/hub/fixtures/contract_backend.py`에 응답 지연·잘못된 신원·받은 frame·연결 수 기록을 더해 쓴다. 독립 기대값: SPEC 매핑 표, 테스트가 준 snapshot 값.

Behavior 순서:
1. 빈 registry → `rows: []`.
2. 꺼진 항목(lock 없음, `backend.json` 없음) → `off`, `last_activity` null. `backend.json` 있으면 mtime.
3. mismatch 4종.
4. 켜진 fixture → `on`, `backend` pid·start_ticks.
5. task·command·last_activity 매핑.
6. waits 매핑과 순서.
7. timeout·snapshot 불일치·identity 오류 → `unknown`.
8. 병렬성·격리(한 행 지연).
9. cache·`fresh`.
10. `pending_requests` `—`.
11. 텍스트 열·label, 손상 registry exit 1.

작성 범위: `src/workbench/hub/{status,presentation,server}.py`, `src/workbench/hub/cli.py`(list), `src/workbench/backend/cli.py`(`_running_snapshot` 함수화만), `tests/hub/test_hub_list.py`, `tests/hub/test_hub_presentation.py`, `tests/hub/fixtures/contract_backend.py`.

독립 test_designer 검증 필수. 초점: 어떤 관측 실패도 `off`로 새지 않는지(연결 거절, 중간 끊김, 잘못된 JSON, 다른 uid peer, pid 재사용), mismatch 판정 순서, 행 간 격리, 관측 연결이 attach된 UI를 방해하지 않음.

## 범위 밖과 중단 조건

켜기·끄기(HB-07), TUI(HB-08), 실제 backend 필드 확인(HB-07 S6, HB-11). backend snapshot 계약을 바꾸지 않는다(필요한 필드가 없으면 멈추고 보고). Hub가 backend 상태를 파일로 저장하지 않는다(cache만).
