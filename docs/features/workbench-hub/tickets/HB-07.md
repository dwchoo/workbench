# HB-07: 프로젝트 제어 라이브러리(켜기·끄기·pause·resume·confirm-boot)

명세: [../SPEC.md](../SPEC.md) s1. 의존성·자원: SPEC "Ticket 그래프"의 HB-07. 상태·실제 assignment는 orchestrator 운영 기록에서만 관리한다.
권장 executor: Opus(`model: "opus"`). backend 수명(켜기로 띄운 backend가 Hub·호출자보다 오래 산다)과 종료 확인 경로다.

## 제공할 동작

`workbench.hub.projects`의 `power_on(entry, attach)`, `power_off(entry, ask, out)`, `pause(entry)`, `resume(entry)`, `confirm_boot(entry)`. 모든 함수는 먼저 `check_entry`로 불일치를 거절한다. 켜기는 기존 `cmd_start`(`--no-attach`, `data_dir=<root>/.wb`), 끄기는 기존 `shutdown_request`/`shutdown_confirm`과 `closing` 결과 대기다. `cmd_shutdown`의 결과 대기 loop를 함수로 빼서 두 곳이 공유한다.

## 수락 기준

- HB-AC-08: 꺼진 프로젝트 `power_on(attach=False)` → backend `ready`, 화면 연결 없음(snapshot `attached:false`), Hub `list`가 `on`. 이미 켜졌으면 두 번째 backend 없음(같은 backend pid, lock holder 불변). backend의 ppid는 호출 driver도 Hub도 아니며, driver·Hub를 끝낸 뒤에도 backend가 산다.
- HB-AC-09: `power_off` → `ask`가 받은 `active`가 `shutdown_request`의 것과 같다. `ask`가 거절 → backend·pane 그대로. 확인 직전 작업 변경(테스트가 host shell에 명령을 넣어 active를 바꿈) → 거절되고 `ask`가 새 목록으로 다시 불린다. 확인 → `verified:true` 결과, backend 종료. 결과 없음·`verified:false`는 성공(0)으로 돌려주지 않는다.
- HB-AC-02: Hub `wb hub stop` 뒤 backend 생존, 새 Hub `list`에서 `on`.
- HB-AC-03: Hub `SIGKILL` 뒤 backend·manager/worker/host pane pid 생존, 프로젝트 안 `wb status --json`이 `ready`.
- HB-AC-13: `mismatch` 항목의 `power_on`·`power_off`는 아무 프로세스도 만들지 않고 거절.
- HB-T02(실물): attach된 UI가 있는 실제 backend에 `pause(entry)` → automation `paused`, UI attach 유지. `resume` → 해제. `confirm_boot`은 보류가 없으면 `boot_confirmation_not_required`를 그대로 돌려준다. 옛 backend의 `not_attached`는 `backend_too_old`로 보고(가짜 controller로 확인).
- 기존 `wb shutdown` 동작·문구 불변(회귀).

## 계약과 맥락

SPEC "프로젝트 제어 라이브러리", "정지 2단계"와 별개인 backend 종료 계약(`service.py:1427-1456`, `cli.py:1010-1121`), `cmd_start`(`cli.py:351-410`), HB-05의 `check_entry`, HB-06의 비attach 허용. 끄기 재시도는 최대 5회. 라이브러리 함수는 출력 stream·`ask` callback을 받아 TUI(HB-08)와 (A) 웹이 같은 절차를 쓴다.

## 검증

Seam S6(실제 backend + fake OMP). 환경은 `tests/recovery_boot/test_live_restart_entrypoint.py:65-96`을 따르되 `.wb` 프로젝트를 쓴다(테스트가 `initialize_project(..., interactive=True, confirm=lambda r: True)`로 만든다). 라이브러리 호출은 테스트가 띄운 driver subprocess(`python -I -c …`, `PYTHONPATH=src`)에서 해서 test runner 안에서 fork하지 않는다. 독립 기대값: `/proc`의 pid·start_ticks·ppid·session, snapshot 값, `backend.json`.

Behavior 순서:
1. 불일치 항목 거절(프로세스 없음).
2. `power_on` → `ready`·`attached:false`·`list on`.
3. 이미 켜짐 → 두 번째 backend 없음.
4. driver·Hub 종료 뒤 backend 생존(ppid 확인).
5. `power_off` 거절 → 불변.
6. `power_off` 확인 → `verified`.
7. 작업 변경 → 재요청·새 목록.
8. Hub `stop`·`SIGKILL` 뒤 생존과 `wb status`(HB-AC-02·03).
9. `pause`/`resume`/`confirm_boot` 실물.
10. `wb shutdown` 회귀.

작성 범위: `src/workbench/hub/projects.py`, `src/workbench/backend/cli.py`(shutdown 대기 함수화), `tests/hub/test_project_control.py`, `tests/hub/fixtures/`(driver).

명령: `python3 tools/shm_tests.py -- env PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src .venv/bin/python -m unittest discover -s tests/hub -p 'test_project_control*.py'`. 회귀: `… discover -s tests/recovery_boot -p 'test_live_restart_entrypoint.py'`, `… discover -s tests/recovery_boot -p 'test_live_shutdown_slow_turn.py'`, `… discover -s tests/backend/installation -p 'test_project_cli*.py'`.

독립 test_designer 검증 필수. 초점: 켜기 경합(두 driver 동시 `power_on`), 켜기 중 Hub 종료, 끄기 token 경합(attach된 UI도 동시에 shutdown 요청), 결과 대기 중 연결 끊김을 성공으로 보지 않음, 작업 변경 재시도 상한.

## 범위 밖과 중단 조건

TUI(HB-08), Hub 쪽 hub_v1 op(예약만, (A)). 새 종료 의미를 만들지 않는다. backend 시작 경로(`spawn_backend`, 시작 요건)를 바꾸지 않는다(바꿔야 하면 멈추고 보고). 실제 OMP·유료 provider를 쓰지 않는다.

## 출력

변경 경로, 명령·결과, behavior별 RED/GREEN, 라이브러리 시그니처와 반환값·사유 코드, 공유한 shutdown 대기 함수, 소유 프로세스 종료 확인.
