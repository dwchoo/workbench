# HB-11: 최종 통합·live·독립 검증

명세: [../SPEC.md](../SPEC.md) s1. 의존성·자원: SPEC "Ticket 그래프"의 HB-11. 상태·실제 assignment는 orchestrator 운영 기록에서만 관리한다.
권장 executor: Sonnet(`model: "sonnet"`) test_designer/검증. 통합 중 발견된 결함은 해당 ticket 범위의 수정 작업으로 되돌리고, 그 ticket의 모델로 고친다.

## 제공할 동작

HB-01~10이 통합된 후보에서 기능 전체를 실제 backend(fake OMP)·PTY로 교차 확인한다. 새 제품 동작은 만들지 않는다.

## 수락 기준

HB-AC-01~19, HB-T01~T08 전부를 SPEC "수락 기준" 표의 책임 ticket 증거와 이번 통합 증거에 연결한다. 추가 최종 확인:
1. S8 PTY e2e(`tests/integration/live_hub_tui.py`): temp HOME에 등록된 두 프로젝트(하나 켜짐, 하나 꺼짐). 프로젝트 밖에서 `wb` → 목록 화면 문자열 확인 → 켜진 행 `Enter` → product UI 진입 → detach → 목록 복귀(프로젝트 backend pid 불변) → 꺼진 행 `Enter` → "켤까요?" → `n` → 목록 유지·backend 없음 → `Enter` → `y` → 켜짐·진입 → detach → 목록에 둘 다 켜짐(HB-AC-08·10·16).
2. 실제 host shell 안의 `wb`(HB-T01): attach된 연결로 host shell pane에 `wb hub start`를 입력 → exit 2 문구, Hub 없음. Hub를 바깥에서 띄운 뒤 같은 pane에서 `wb hub status` → 실행 중.
3. 실제 backend 필드 drift: 실제 backend snapshot으로 만든 행의 `task`·`command`·`waits`(pause 상태 포함)가 SPEC 매핑과 맞는다(HB-AC-12).
4. Hub `SIGKILL`·`wb hub stop` 뒤 프로젝트 안 `wb`(PTY)로 직접 연결(HB-AC-03).
5. 회귀 넓게 한 번(디렉터리별, `-t .` 없음): `tests/hub`, `tests/backend`(모듈 범위별), `tests/backend/installation`, `tests/backend/maintenance`, `tests/ui`, `tests/recovery_boot`, `tests/contracts`.
6. `*_independent*` 테스트 중 CLI subprocess를 띄우는 파일에 `WORKBENCH_HUB_AUTOSTART=0`을 test_designer가 넣고, 전체 실행 뒤 남은 Hub 프로세스가 없음을 `/proc`에서 확인한다.
7. `pending`: 실제 재부팅 뒤 `wb hub enable` 동작(HB-AC-04), 실제 `uv tool install` 재설치 뒤 새 version Hub(HB-AC-18). 이 host에서 실행할 수 없으면 `not_run`으로 보고하고 다른 증거로 대체 주장하지 않는다.
8. Acceptance trace 표를 `docs/features/workbench-hub/VERIFICATION.md`에 남긴다.

## 계약과 맥락

SPEC 전체. 최종 검토: Standards·Spec 두 fresh reviewer가 같은 frozen 후보·전체 diff(새 파일 포함)를 본다. 새 local socket(hub_v1), 프로세스 신원, 비attach 제어가 security trigger이므로 별도 security reviewer와 diff secret scan을 둔다(위협: 같은 uid 밖의 socket 접근, stale record·pid 재사용으로 다른 프로세스 신호, 관리 tree 탈출 실패, client 이름 위조로 attach 필요 요청 우회, registry 경로 조작으로 다른 폴더 초기화·삭제). Scope audit: `.wb` 구조·`backend.json`·SQLite·설치 manifest 불변, `omp-workbench/` runtime base 아래 Hub 파일 없음.

## 검증

실제 프로세스·PTY·fake OMP. 독립 test_designer가 요구에서 도출한 최종 시나리오를 먼저 확인한다. 실패는 원인(코드·테스트·환경·계약)을 분류해 해당 ticket 수정으로 돌리고 orchestrator가 판정한다. 같은 후보·환경에서 통과한 근거를 반복 실행하지 않는다.

명령(repo 루트, 접두사 `python3 tools/shm_tests.py -- env PYTHONDONTWRITEBYTECODE=1 PYTHONPATH=src .venv/bin/python`): SPEC "테스트 결정"의 명령 전부 + `… -m unittest discover -s tests/integration -p 'live_hub*.py'`. `tests/gates`는 쓰지 않는다. 작성 범위: `tests/integration/live_hub*.py`, `*_independent*` 파일(test_designer 소유), `docs/features/workbench-hub/VERIFICATION.md`.

## 범위 밖과 중단 조건

새 기능, (A), 운영 배포, commit/push, Docker, 새 도구 설치, 실제 사용자 systemd 조작. 필수 runtime이 없으면 해당 항목은 `not_run`이고 성공으로 보지 않는다. 테스트가 만든 process·temp dir을 정리하고 `.workflow` 용량을 확인한다.

## 출력

후보 id, 각 확인의 명령·exit code·개수·시간, `not_run` 항목과 이유, review·security 결과 요약, acceptance trace, 남은 Hub·backend 프로세스 없음 확인.
