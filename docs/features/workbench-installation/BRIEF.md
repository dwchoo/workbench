# Workbench 설치와 프로젝트별 사용 — 요구사항 합의 초안

Revision: r0.4; state: agreement requested (개별 합의와 최종 확인할 추천안을 구분).
작성일: 2026-10-19. 이 문서는 설치·사용 개선을 위한 discovery이며 제품 구현·설치 실행·기존 상태 이관·commit·배포 권한이 아니다. 전체 BRIEF 승인은 아직 받지 않았다. 사용자 답변은 [결정 기록](../../../.workflow/workbench-installation/runs/refine-20261019/decisions.json)에 별도로 보존한다.

## 문제, 사용자와 목표

연구 프로젝트에서 Workbench를 사용하는 사용자는 프로젝트 환경에 WB 자체를 설치하거나 WB 내장 skills를 배치하지 않고도 독립 프로그램처럼 실행하기를 원한다. 설치에는 필수 OMP의 점검과 미설치 시 설치까지 포함되어야 한다. 작업 이력·DB·로그는 모든 프로젝트가 하나의 상태 저장소를 공유하지 않고 프로젝트별로 구분되어야 한다.

목표는 uv 기반의 독립 설치, WB가 안내·처리하는 OMP 준비, 프로젝트 로컬 상태를 결합하는 것이다. 프로젝트는 첫 실행 폴더를 확인받아 초기화하고 이후 가장 가까운 `.wb/`를 찾아 연결한다. OMP는 실행 가능한 기존 설치를 재사용하고 없으면 프로젝트 밖 WB 전용 위치에 공유 설치한다. 나머지 미결정 동작은 아래에서 구분한다.

## 공통 용어

[CONTEXT.md](../../../CONTEXT.md)의 WB 설치본, WB 내장 skill, WB 프로젝트 상태, WB 프로젝트 root, WB 상태 이관, 실험 환경, 화면 분리와 Workbench 종료를 따른다.

## 범위와 비목표

- 합의된 포함 범위: Git 저장소의 버전을 `uv tool install`로 독립 설치, 설치본과 연구 프로젝트의 분리, WB 내장 skills의 설치본 관리, 프로젝트별 `.wb/` 상태 저장, Git 추적 제외, `wb setup`의 OMP 점검·미설치 시 최신 stable 설치, 원본 보존 방식의 기존 상태 이관 기능.
- 제품 자산에는 skill reference·helper도 포함한다. 프로젝트에 WB 내장 skill 디렉터리를 복사해야만 사용할 수 있는 구조로 만들지 않는다.
- 구체화 대상: 프로젝트 식별과 초기화·재접속, 설치 자산의 배포, OMP의 위치·버전·인증 경계, 기존 CLI와 data-dir의 호환, 임시 runtime 파일의 위치, 설치·사용 안내와 실패 복구.
- 비목표: Phase 2, Windows, 내부 tmux 도입, 프로젝트 Python 의존성 관리 대행, 기존 사용자 로그의 무단 이관·삭제, raw 보관 정책 변경, 설치 중 연구 작업 자동 실행.
- PyPI 배포 준비는 이번 범위에서 제외한다(WI-D10). 실제 게시·배포 실행은 이 문서 작업의 권한이 아니다.
- 시스템 서비스 자동 등록, 원격 공유 상태 지원, uvx를 통한 장기 backend 운영 보장, live 상태 이관·이력 병합·자동 분할·프로젝트 폴더 이동 후 자동 경로 복구, 제품 uninstall 기능은 후속 범위로 유보하는 안을 제안한다(WI-P07, 최종 확인 대기).

## 제약과 호환성 약속

- Python 중심·Linux 우선, 내부 외부 multiplexer 비의존과 기존 Manager/Worker 역할을 유지한다.
- WB 설치 환경을 연구 프로젝트의 Python/conda/venv 환경으로 주입하지 않는다. 기존 부모 persistent shell·입력 owner·pause·no replay·detach·종료 계약을 유지한다.
- 설치본 자산과 프로젝트의 가변 상태를 구분한다. 프로젝트마다 WB 자체를 다시 설치하지 않는다.
- `.wb/`는 Git 추적에서 제외한다. 기존 추적 파일·ignore 설정을 훼손하지 않고 적용하는 구체 방법은 planning에서 선택한다. 기존 파일 충돌 처리의 추천안은 WI-P03이다.
- 인증은 기존 OMP 활용 계약을 유지한다. 인증 자료를 프로젝트로 복사하거나 새 WB credential 저장소를 만드는 권한으로 해석하지 않는다. 로그인 절차와 경로 연결의 상세는 추가 결정 대상이다.
- 로그 위치 분리는 raw rotation 활성화나 기존 로그 삭제 승인이 아니다. [기존 로그 BRIEF](../dev-validation-log-retention/BRIEF.md)의 별도 활성화·보존 조건을 유지한다.
- OMP 바이너리 배포 방식만으로 공개 TS extension·SDK 경로의 호환을 단정하지 않는다. 채택할 방식은 설치 후 해당 경계 검증이 필요하다.

## 합의된 공개 동작과 수락 예시

다음은 개별 답변에서 확정된 요구다. 전체 동작 명세와 최종 수락 기준은 미결정 해소 후 정리한다.

- WI-AC-01: 사용자가 Git 저장소의 tag 또는 commit으로 `uv tool install`하여 WB를 설치할 수 있다. 사용 대상 연구 프로젝트에 WB를 Python 의존성으로 추가하거나 WB 개발 checkout을 유지해야만 실행되는 구조를 요구하지 않는다. 저장소 접근 인증과 uv 자체 설치는 사전 요건이며 실행 명령의 최종 확인안은 WI-P05다.
- WI-AC-02: 설치본이 제공하는 WB 내장 skills·references·helpers를 프로젝트에 설치·복사하지 않고 사용할 수 있다. 기존 역할별 노출과 사용자 전용 report 호출 계약은 유지한다.
- WI-AC-03: 프로젝트별 작업 이력·DB·로그는 해당 프로젝트의 `.wb/`에 보관하고 Git 추적에서 제외한다. A와 B 프로젝트의 이력을 하나로 합치지 않는다. Git 제외의 구체 방법은 planning에서 선택한다.
- WI-AC-04: uv로 WB를 설치한 후 사용자는 `wb setup`으로 필수 OMP를 점검하고, OMP가 없으면 이 흐름에서 설치한다. 사용자가 별도로 OMP 설치 명령을 찾아 실행하는 것을 기본 사용 절차로 요구하지 않는다. 미호환 처리와 설치 실패 복구는 추가 구체화 대상이다.
- WI-AC-05: 초기화된 WB 프로젝트가 없을 때 첫 실행 폴더를 표시하고 사용자 확인 후 그곳에 `.wb/`를 생성한다. 사용자가 거절하면 생성·시작하지 않는다. Git 저장소가 아니어도 사용할 수 있으며 Git root를 강제하지 않는다. (갱신: [Hub BRIEF](../workbench-hub/BRIEF.md) HB-D08과 [Hub SPEC](../workbench-hub/SPEC.md) CLI 계약이 인자 없는 `wb`의 프로젝트 밖 동작을 대체한다. 이제 프로젝트 밖의 `wb`는 초기화를 묻지 않고 Hub 목록을 열며, 새 프로젝트는 `wb init` 또는 명시한 `wb start`로 만든다. 확인 후 생성·거절 시 미생성 규칙은 `wb init`과 `wb start`에 그대로 적용된다. 이전 문구는 이력으로 보존한다.)
- WI-AC-06: 현재 폴더부터 상위 폴더까지 가장 가까운 초기화된 `.wb/`를 찾아 같은 프로젝트에 연결한다. 예를 들어 `research/.wb/`가 있으면 `research/src/`에서 실행해도 새 프로젝트 상태를 만들지 않는다. 중첩 프로젝트의 새 초기화를 명시하는 수단과 기존 `.wb/`가 유효하지 않을 때의 동작은 추가 구체화 대상이다.
- WI-AC-07: 실행 가능한 기존 OMP가 있으면 재사용한다. 없으면 WB 전용 사용자 위치에 설치하고 여러 프로젝트가 공유한다. 기존 설치를 덮어쓰거나 프로젝트마다 OMP 프로그램을 복제하지 않는다. 실행 불가·호환 실패는 단순 미설치와 구분해 처리하며 상세 정책은 미결정이다.
- WI-AC-08: 새 OMP 설치는 설치 시점의 최신 stable 버전을 대상으로 한다. 설치 후 업데이트는 명시적으로 수행하며 WB 시작마다 자동 업데이트하지 않는다. 기존 실행 가능한 OMP는 유지한다. 새 버전을 실제 WB 호환 검증 통과로 표시하지 않는다.
- WI-AC-09: 기본 저장 위치는 WI-AC-05~06의 프로젝트 `.wb/`다. 기존 data-dir의 기록을 사용자가 지정한 프로젝트의 `.wb/`로 이관하는 기능을 제공한다. 자동 이관하지 않는다. 원본을 보존한 채 복사·검증 후 새 `.wb/`를 사용하고 원본 삭제는 별도 결정으로 남긴다. 대상 충돌·실행 중 상태 처리와 구체 명령은 최종 확인안 WI-P04를 따른다.

### 최종 확인할 경계 동작 추천안

다음은 이미 승인된 결정으로 간주하지 않는다. 이번 BRIEF 전체 합의에서 사용자 확인을 요청하는 제안이며 수락 기준에도 같은 상태를 적용한다.

- WI-AC-10 / WI-P01: DB·로그·Task 상태·OMP 대화 세션 등 이어서 작업하는 데 필요한 영속 자료는 프로젝트 `.wb/`에 둔다. WB 프로그램·내장 skills·agents·bridge는 설치본에서 제공하고, 재생성 가능한 cache·socket 등은 프로젝트 밖 사용자 전용 경로에서 프로젝트별로 격리한다. 인증은 기존 OMP 저장소를 활용하며 비밀 자료를 프로젝트로 복사하지 않는다. 디렉터리 이름·OS별 경로는 planning에서 정하되 긴 프로젝트 경로만으로 UDS 길이 상한에 걸리지 않아야 한다.
- WI-AC-11 / WI-P03: 기존 `.wb/`가 유효한 WB 상태가 아니거나 사용자 파일과 충돌하면 덮어쓰지 않고 원인·경로를 안내한다. 다른 프로젝트로 조용히 넘어가거나 자동 초기화하지 않는다. Git 제외 적용이 실패하거나 이미 추적된 자료가 있으면 표시하고 임의로 untrack·삭제하지 않는다. Git 없는 디렉터리에도 초기화할 수 있다.
- WI-AC-12 / WI-P04: 이관은 하나의 기존 data-dir을 하나의 대상 프로젝트로 전환한다. 원본·대상의 backend와 관련 쓰기가 중단된 상태에서만 진행하고 실행 중이면 사용자가 종료하도록 안내한다. 대상에 기존 이력이 있으면 덮어쓰기·병합하지 않는다. 원본과 대상의 중첩도 거절한다. 복사·영속 기록 검증·경로 연결 재설정이 성공해야 완료로 표시하며 실패 시 원본을 보존하고 대상의 미완료 상태를 표시한다. 외부 실험 결과·worktree는 자동 이동하지 않고 기존 출처를 유지하며 접근할 수 없는 참조는 미확인으로 알린다. socket·PID·실행 승인을 그대로 가져와 명령을 replay하지 않는다. 구체 명령·검증 manifest·원자적 완료 표시는 planning에서 정한다.
- WI-AC-13 / WI-P05: `wb`를 기본 진입점으로 제공하고 인자 없이 실행하면 프로젝트 초기화 확인 또는 기존 backend의 시작·연결로 이어진다. `wb setup`, `wb start`, `wb attach`, `wb status`, `wb shutdown`을 제공한다. 기존 `omp-workbench` 명령·명시 `--data-dir`·`WORKBENCH_DATA_DIR`를 유지하고 우선순위는 명시 옵션 > 환경 변수 > 프로젝트 탐색으로 한다. 명시 저장소 사용 시 실제 프로젝트와 경로를 표시한다. README에는 설치·setup·첫 실행·하위 폴더 재접속·detach·일시정지·전체 종료·이관·로그 위치와 종료 후 업데이트 절차를 설명한다. 별도 `doctor` 명령을 추가하는 범위로 확대하지 않는다. (갱신: [Hub BRIEF](../workbench-hub/BRIEF.md) HB-D08과 [Hub SPEC](../workbench-hub/SPEC.md) CLI 계약이 인자 없는 `wb`의 프로젝트 밖 동작을 대체한다. 이제 프로젝트 밖의 `wb`는 초기화를 묻지 않고 Hub 목록을 열며, 새 프로젝트는 `wb init` 또는 명시한 `wb start`로 만든다. 확인 후 생성·거절 시 미생성 규칙은 `wb init`과 `wb start`에 그대로 적용된다. 이전 문구는 이력으로 보존한다.)
- WI-AC-14 / WI-P06: `wb setup`은 명시 OMP 경로·기존 WB setup 선택·PATH의 기존 설치를 확인하고 실행 가능한 OMP를 재사용한다. 새로 설치하는 경우 사용자 전용 WB 관리 경로에 최신 stable 및 필요한 runtime 의존성을 준비하며 sudo·기존 설치 덮어쓰기를 요구하지 않는다. 설치 경로·실제 버전·준비 결과를 표시한다. 다운로드·무결성·실행 확인 실패는 실패로 표시하고 재시도 방법을 안내한다. 기존 실행 파일이 고장났거나 실제 WB 호환 문제가 확인되면 원인을 표시하고 조용히 교체하지 않는다. 버전이 검증 이력과 다르다는 이유만으로 강제 교체하거나 호환 통과로 표시하지 않는다. 로그인은 OMP 인증 흐름을 안내해 사용자가 진행하며 설치 과정에서 모델 작업·연구 실험을 시작하지 않는다. setup 없이 실행 요건이 부족하면 setup 안내로 멈추고 첫 start에서 몰래 설치하지 않는다.
- WI-AC-15 / WI-P07: 중첩 프로젝트를 새로 만드는 전용 명령, 실행 중 폴더 이전, 임의 프로젝트 복제·경로 변경의 자동 복구, 여러 프로젝트 이력의 병합·분할은 이번 범위에서 제외한다. 인식한 프로젝트 root·실제 프로세스·기록 경로가 불일치하면 상태를 알리고 자동 실행·잘못된 backend 연결을 보류한다. 설치본 업데이트·교체는 backend 종료 후 수행하도록 안내하고 실행 중 자동 업데이트하지 않는다. 이전 버전으로 DB를 열 수 있다는 보장은 하지 않는다.

## 구현 방향과 검증 의도

상세 구현·ticket 배치는 후속 planning의 범위다. 다음 관측 가능한 경계를 검증 대상으로 고려한다.

- 개발 checkout이 없는 환경에서 uv로 설치한 WB가 다른 연구 프로젝트에서 실행되며 내장 자산을 찾는다.
- 연구 프로젝트의 활성 Python 환경을 WB 의존성으로 바꾸지 않는다.
- 프로젝트 간 상태·OMP 세션·backend 재접속이 섞이지 않는다. 동일 프로젝트의 중복 실행 경계와 명시적 전체 종료를 유지한다.
- `wb setup`은 OMP 유무와 실행 가능 여부를 구분한다. 실패를 성공으로 표시하지 않는다. 채택 배포 방식의 TS extension·SDK 경계를 검증한다.
- `.wb/`의 Git 제외, 임시 runtime 자료·인증 자료와 영속 상태의 분리, 긴 경로·권한 실패·기존 상태 호환은 결정 후 수락 예시를 보강한다.
- 이관에서는 DB·로그·OMP 세션 등 영속 자료와 socket·PID·프로세스 기록·인증 연결 등 재생성하거나 재대조할 자료를 구분한다. 이관만으로 실험·명령을 재실행하지 않는 기존 no replay 경계를 검증한다. 원본 보존은 확정되었고 대상 충돌·실행 중 거절·실패 복구는 WI-P04의 최종 확인을 기다린다.

## 저장소 관측과 외부 근거

기준 snapshot: HEAD `810cf72`, 2026-10-19 읽기 조사. 기존 workflow·skill 설정 등 사용자 변경은 별도이며 이 기능으로 변경하지 않는다.

- `pyproject.toml`: Python >=3.12, console entry point `omp-workbench`, `src`의 Python package 검색만 선언되어 있다. `wb`·`setup`은 현재 CLI가 아닌 이번 합의의 신규 인터페이스다.
- `src/workbench/backend/launcher.py`의 `_repository_root`·`default_skills_dir` 및 `src/workbench/backend/omp_home.py`의 `default_agents_dir`: bridge·skills·agents 자산을 개발 저장소 위치에서 찾는다. 독립 패키지 설치 시 보완 필요성은 정적 추론이며 이번 작업에서 새 환경 설치 시험을 한 것은 아니다.
- `src/workbench/backend/paths.py`의 `resolve_data_dir`: 현재 기본은 사용자 state 디렉터리이며 cwd에 따른 프로젝트 자동 분리가 없다. `DataLayout`은 socket과 영속 DB·로그를 같은 root에 둔다. UDS 경로는 107 bytes 상한을 확인한다.
- `src/workbench/backend/cli.py`: `start`·`attach`·`status`·`confirm-boot`·`shutdown` 등 기존 명령이 있으며 setup·doctor 명령은 없다. 기존 backend가 있으면 data-dir을 기준으로 재접속한다.
- `src/workbench/backend/omp_home.py`: 현재 가변 OMP home은 data-dir에 생성하고 사용자 OMP auth store를 링크한다. `omp_bridge/skills/README.md`: WB 내장 skills만 허용하는 기존 역할별 격리 계약을 기술한다.
- 추가 읽기 조사: `src/workbench/backend/service.py`의 `_record`는 data-dir·project-dir·socket·process 정보를 기록하고, `src/workbench/tasks/repository.py`와 `src/workbench/storage/log_raw/{store,segments}.py`는 DB·로그 저장소를 각 root에 연결한다. 이관을 단순 폴더 복사로 완료할 수 있다는 검증은 하지 않았다. 인증 파일은 읽거나 복사하지 않았다.
- [uv tools](https://docs.astral.sh/uv/concepts/tools/): tool install은 프로젝트와 분리된 지속 설치 환경을 사용한다. uvx는 cache의 임시 환경을 사용하므로 장기 backend와 자산 수명의 별도 검토가 필요하다.
- [uv tool 설치 안내](https://docs.astral.sh/uv/guides/tools/#installing-tools): package·Git source 설치와 CLI 노출을 설명한다. WB가 배포·동작 검증을 마쳤다는 근거는 아니다.
- [OMP 공식 설치 script](https://github.com/can1357/oh-my-pi/blob/main/scripts/install.sh): Bun 기반 설치 및 release binary 다운로드·checksum 검증 방식을 제공한다. 현재 upstream 문서 관측이며 WB가 사용할 구체 방식·버전의 호환을 검증한 결과는 아니다.

## 미결정과 유보의 영향

- WI-P01, WI-P03~07은 최종 확인 대기다. 사용자가 변경·거절하면 해당 저장·설치·이관·호환 경계를 다시 정하고 그 전까지 관련 planning 수락 기준을 확정하지 않는다. WI-D01~10의 기존 합의는 유지한다.
- 제안대로 합의하면 구체 경로·초기화 marker 형식·Git 제외 구현·설치 backend·필요한 runtime 종류·이관 명령과 완료 검증 방법은 후속 planning의 기술 상세다. 관측하지 않은 OMP 배포 방식의 extension·SDK 호환을 검증 통과로 가정해서는 안 된다. 최신 stable 설치 요구를 검증 버전 pin으로 조용히 대체하지 않는다.
- PyPI는 이번 범위에서 제외했다. 제안된 uvx·systemd·원격 공유·중첩 프로젝트 생성·live 이전·병합·분할·복제 경로 자동 복구 유보를 합의하면 해당 동작을 제품 지원으로 약속하지 않는다. 기존 상태 원본 정리도 자동화하지 않는다.
- `.wb/`의 로그 정책은 기존 정책을 적용한다. 용량·보존 정책 변경이나 raw rotation 활성화는 이번 합의에 포함하지 않는다.
