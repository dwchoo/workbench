# WI-04: wb setup의 OMP 점검과 사용자 전용 설치

Specification: [SPEC.md s1](../SPEC.md). Scheduling: [PLAN.json p1](../PLAN.json)의 `WI-04` 항목이 유일한 dependency/resource 원본이다.
상태: bundle 승인 대기인 계획 초안. 실행 상태·writer·후보·검증은 Root의 `.workflow/workbench-installation/` 기록에서 관리한다.

## 제공 동작

명시 --omp/WORKBENCH_OMP > 기존 setup 선택 > PATH 순으로 기존 설치를 점검한다. 후보가 있되 고장났으면 별도 실패로 표시하고 몰래 새 설치로 바꾸지 않는다. 없을 때만 WI-01 recipe에 따라 사용자 전용 경로에 runtime까지 준비한다. 반복 setup은 재사용하며 일반 start에는 다운로드가 없다.

산출물: 기존 OMP 우선 재사용, 없으면 당시 stable을 검증 후 준비하고 상태·실패·로그인을 안내하는 setup.

## 수락 기준

WI-AC-04, WI-AC-07, WI-AC-08, WI-AC-13, WI-AC-14. [SPEC의 전체 acceptance trace](../SPEC.md#수락-기준)의 해당 행을 적용하며 생략하지 않는다.
이 ticket의 local 관측과 후속 integration 관측을 구분한다. 완료 표시만으로 사용자 수락을 충족하지 않는다.

## 계약과 관련 맥락

SPEC §setup의 위치·transaction·상태 경계, WI-01 recipe와 WI-02 설치 자산을 소비한다. stable은 transaction 시작 시 resolve하여 한 버전으로 고정하고 actual CLI/SDK 버전과 integrity를 검증한 후 active 선택을 교체한다. user prefix의 설치 lock, staging, atomic 선택·rollback을 적용하고 shell rc/PATH나 기존 설치는 수정하지 않는다. 명시적 후속 OMP 업데이트는 선택된 설치 방식의 안내로 제공하며 새 update 명령을 만들지 않는다.

BRIEF r0.4의 WI-D01~10은 개별 사용자 결정이다. WI-P01/P03~07와 SPEC의 기술·test seam 제안은 전체 bundle 확인 대기이며 이 ticket 파일의 존재가 승인은 아니다.
구체 write 범위는 PLAN의 `write_scope_hint`를 출발점으로 Root가 dispatch 직전 실제 base/dirty files와 대조한다. 기존 사용자 변경을 보존한다.

## 검증

선택·재사용·새 설치·checksum mismatch·불완전 metadata·네트워크 실패·중단·동시 setup·권한 실패·로그인 미완료를 public setup CLI에서 behavior별 RED → 최소 GREEN. fault fixtures는 local HTTP 또는 주입 가능한 installer transport를 사용한다. G-WI-05는 실제 stable 다운로드/설치와 설치본 SDK load를 격리 HOME에서 관측하며 fake success로 대체하지 않는다. 준비 성공은 인증 또는 모든 모델 호환 성공을 뜻하지 않는다.

소유 gate: G-WI-04, G-WI-05. required evidence level·supplier는 PLAN gate 항목을 따른다. 소유 gate는 자신의 산출물과 transitive predecessors만 요구하며 이후 통합 G-WI-10/11을 앞 ticket의 완료 조건으로 역참조하지 않는다.

예정 명령(이 planning에서는 실행하지 않음; 새 경로는 이 ticket 또는 명시된 prerequisite가 작성):

```sh
PYTHONPATH=src:. python3 -m unittest discover -s tests/backend/installation -p 'test_setup.py' -v
PYTHONPATH=src:. python3 tests/backend/installation/live_setup.py --run-root <owned-run-root>
```

일반 behavior는 Root가 실제 `.agents/skills/tdd/SKILL.md` identity와 승인된 SPEC test seam을 packet에 넣어 한 행동의 RED → 최소 GREEN → 다음 행동 순서로 수행한다.
RED의 원인·당시 후보/명령, 최소 production delta, GREEN 후보/명령을 남긴다. unrelated import/도구 오류를 의미 있는 RED로 주장하지 않는다.
독립 test_designer는 worker 구현을 정답으로 복제하지 않고 승인된 요구·독립 expected values에서 검증을 평가/보완한다. coherence unit의 fresh general review와 최종 feature의 Standards/Spec pair, 해당 security review는 Root가 계약 §7에 따라 수행한다.

## 제외 범위와 중단 조건

stable 확인/무결성 자료/SDK 경계가 없으면 setup 실패로 남긴다. 지원하지 않는 Linux 배포/arch에서는 원인과 안내를 반환하며 sudo fallback을 추가하지 않는다. 최신 stable 선택·기존 설치 보존을 침해하는 workaround는 중단한다.

새 제품 결정·test seam 변경·승인 범위 밖 의존성이 필요하면 Root에 근거와 영향 ticket/gate를 전달한다. leaf는 workflow 재진입·추가 위임하지 않는다.
