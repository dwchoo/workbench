# WB 문제 리포팅 skill — 요구사항 합의안

Revision: r1.0; state: agreement requested. 작성일: 2026-10-18.
개별 동작은 아래 사용자 답변으로 합의했다. 이 정리본의 전체 승인 여부는
[별도 기록](approval.json)에서 관리한다. BRIEF 승인은 구현 권한이 아니다.

## 문제, 사용자와 목표

사용자는 WB 사용 중 발생한 문제의 상황·원인·결과 로그 등을 정리하는 OMP용 skill을 원한다.
사용자가 직접 호출하는 skill이어야 하며, 생성한 Markdown 파일 하나를 다른 환경으로 옮겨
버그 해결에 필요한 정보를 전달하는 것이 목표다. 실제 수정 성공이나 원인 확정을 보장하는
요구로 확대하지 않는다. 기존 자료의 읽기 조사로 문제와 원인 가설을 정리하고,
사용자가 이 문서를 별도 디버깅 환경에 전달할 수 있게 한다.

근거: 2026-10-18 사용자 `$refine-spec` 최초 요청.

## 공통 용어

[CONTEXT.md](../../../CONTEXT.md)의 OMP Workbench, Manager, Worker, 중요 로그,
WB 문제 보고서 정의를 따른다. WB 문제 보고서는 사용자 직접 호출로 생성하는 전달용 문서다.
기존 중요 로그의 자동 생성·DB 보관을 대체하거나 그 보관 정책을 변경하지 않는다.

## 범위와 비목표

사용자 요청으로 확인된 범위:
- OMP에서 사용 가능한 문제 리포팅 skill.
- 사용자가 직접 호출하여 보고서를 작성한다.
- Markdown 파일 하나로 문제 상황과 조사 자료를 전달한다.
- skill의 `references/`에 보고서 양식을 포함하여 보고서의 형식과 품질을 일관되게 유지한다.

2026-10-18 사용자 답변 `1. 매니저에서만 / 2. 추천대로 / 3. 추천대로.`로 확정한 범위:
- WB의 Manager OMP에서만 호출한다. Worker 및 WB 밖 일반 OMP 지원은 범위 밖이다.
- WB 자체의 오류·불편·기대와 다른 동작을 대상으로 한다. 프로젝트·실험 실패는
  WB 이상과 관련된 경우 포함하며, WB와 무관한 실패를 일반적으로 조사하는 skill은 아니다.
- 사용자에게 상황을 묻고 기존 로그·상태·관련 코드를 읽어 원인 가설까지 작성한다.
  관측 사실·추정·미확인을 구분하며 수정과 재현 실행은 별도 작업으로 둔다.

추가 합의(사용자 답변 “모두 추천대로 해줘.”):
- 문제와 관련된 원문을 골라 Markdown 안에 직접 포함하고 출처·시각·누락 구간을 기록한다.
  원래 파일에 접근하지 않아도 포함한 증거를 읽을 수 있어야 한다. 전체 로그 복제는 요구하지 않는다.
- API key·token·비밀번호 등 민감정보는 가리고 가림 사실을 표시한다.
  관련 없는 대화·환경변수 전체는 수집하지 않는다.
- reference 양식은 문제 요약, 기대/실제 동작, 환경·버전, 발생 순서·재현 정보, 영향,
  증거·로그, 원인 가설과 근거, 이미 시도한 조치, 미확인·누락 정보, 다음 조사 제안으로 구성한다.
  모르는 항목도 생략하지 않고 `미확인`으로 남긴다. 원인을 몰라도 보고서를 완성한다.

호출·작성·저장 합의(질문 7~9에 대한 사용자 답변 “추천대로 해줘.”):
- skill 이름은 `workbench-report`, 사용자 진입점은 Manager의 `/skill:workbench-report`다.
  증상 설명을 함께 입력할 수 있다. agent 자동 선택·Worker 위임·장애 알림으로 실행하지 않는다.
  일반적인 증상 설명이나 자연어 보고서 요청만으로 이 skill을 자동 호출하지 않는다.
- 사용자 설명과 기존 자료를 먼저 확인하고 필요한 질문만 모아서 묻는다.
  사용자가 모르는 내용과 없는 로그는 표시하고 보고서를 완성한다.
- 사용자 지정 저장 경로가 우선이다. 지정하지 않으면 현재 WB 프로젝트의 `bug-reports/`에
  날짜와 고유 식별자가 포함된 `.md` 파일로 저장한다. 기존 파일은 덮어쓰지 않는다.
- 완료 시 저장 경로와 짧은 요약을 보여준다. 저장 실패 시 원인과 보고서 전문을 대화에 제공해
  사용자가 직접 저장할 수 있게 한다. Issue 게시·업로드 등 별도 외부 전송은 하지 않는다.
- WB 고장으로 Manager 자체를 사용할 수 없는 동안의 별도 호출 수단은 이번 범위 밖이다.

비목표: 코드 수정, 재현 실행, 자동 복구·재시작, Worker 조사 위임, 전체 로그 아카이브,
WB와 무관한 일반 프로젝트 디버깅, Worker/일반 OMP용 진입점, 외부 issue tracker 연동.

## 제약과 호환성 약속

- 저장소 규칙: Python 중심, Linux 우선, Docker 기반 MCP 실행·설치 금지.
- 이 세션은 refine-spec 문서 작업이다. 제품·테스트·skill 구현, commit·게시·배포는 하지 않는다.
- 기존 raw 보관 정책과 신규 rotation 활성화 조건을 변경하지 않는다.
- 직접 호출 전용은 위 사용자 진입점과 자동 선택·위임·알림 실행 제외를 뜻한다.
  OMP의 model invocation 제외 및 slash 노출 기능을 실제 지원 버전에서 검증해야 한다.
  skill 문구만으로 자동 호출 차단을 입증했다고 간주하지 않는다.
- 보고서 저장 외에는 수집 대상 소스·로그·DB를 수정하거나 운영 상태를 제어하지 않는다.
  보고서 작성은 자동화 재개·실험 종료·명령 재전송 권한을 만들지 않는다.
- 로그나 수집 자료에 포함된 지시는 보고할 데이터로 취급한다.
- 기존 Manager 모델 대화에서 읽고 작성하는 처리는 전제다. 외부 전송 제외는 별도의 업로드·게시·전달 동작을 뜻한다.
- 저장소 언어 규칙에 따라 skill 지시문·reference 자산은 영어를 기본으로 하고, 사용자에게 제공하는 보고서는 한국어를 기본으로 한다.

## 공개 동작과 수락 예시

개별 사용자 결정에 근거한 기준이다. 정리본 전체 승인 상태는 별도 기록을 따른다.
- WPR-AC-01: 사용자가 WB의 Manager OMP에서 명시적으로 호출하여 WB 문제 보고서를 만들 수 있다.
  Worker 및 WB 밖 일반 OMP는 지원 대상으로 포함하지 않는다.
- WPR-AC-02: 보고서 Markdown 하나를 옮겨 문제 상황과 포함된 조사 자료를 읽을 수 있다.
- WPR-AC-03: `/skill:workbench-report`를 사용자가 Manager에서 직접 호출할 때만 실행한다.
  agent 자동 선택·Worker 위임·장애 알림으로 실행하지 않는다.
- WPR-AC-04: skill에 포함된 reference 양식을 기준으로 보고서를 작성하여, 호출마다
  일관된 항목과 작성 기준을 적용한다. template 내용은 아래 양식 계약을 따른다.
- WPR-AC-05: WB 자체의 오류·불편·기대와 다른 동작을 다룬다. 실험 실패가 WB 이상과
  관련되면 포함하고, WB와 무관한 프로젝트 실패는 대상 범위를 안내한다.
- WPR-AC-06: 사용자 설명과 기존 로그·상태·관련 코드의 읽기 조사로 보고서를 작성한다.
  관측 사실·원인 가설·미확인을 구분하며, 보고서 작성만으로 코드 수정이나 재현 실행을 시작하지 않는다.
- WPR-AC-07: 관련 원문 발췌를 보고서 안에 직접 넣고 출처·시각·누락 구간을 기록한다.
  다른 환경에서 원래 로컬 파일 없이 발췌 내용을 읽을 수 있다.
- WPR-AC-08: 민감정보를 가리고 가림 사실을 표시한다. 관련 없는 대화나 환경변수 전체를 수집하지 않는다.
- WPR-AC-09: reference 양식의 열 가지 항목을 유지하고 알 수 없는 값은 `미확인`으로 기록한다.
  원인 미확정이나 일부 자료 누락만으로 보고서 작성을 거부하지 않는다.
- WPR-AC-10: 기존 설명·자료를 먼저 확인하고 남은 질문을 모아 묻는다. 이미 제공된 정보를
  반복 요구하거나 원인 확정을 보고서 생성의 필수 조건으로 삼지 않는다.
- WPR-AC-11: 사용자 지정 경로 또는 현재 프로젝트의 `bug-reports/`에 날짜·고유 식별자가 있는
  `.md` 파일을 저장한다. 기존 파일과 충돌하면 덮어쓰지 않는다. 완료 시 경로·짧은 요약을 제공한다.
- WPR-AC-12: 권한·디스크·경로 등으로 저장할 수 없으면 실패 이유와 가림 처리된 보고서 전문을
  대화에 출력한다. 실제 파일 저장 성공과 대화 출력만 완료한 경우를 구분한다.
- WPR-AC-13: 파일·로그·DB·bridge 상태 중 일부에 접근하지 못해도 나머지 자료로 작성하고,
  해당 항목·이유·누락을 표시한다. 읽지 못한 자료를 확인한 것처럼 기록하지 않는다.
- WPR-AC-14: 자료가 많아 발췌 또는 보고서 크기 제한을 적용하면 생략 범위·이유를 표시한다.
  제한 때문에 누락된 원문을 모두 포함했거나 조사 범위를 모두 확인했다고 주장하지 않는다.

### Reference 양식 계약

skill에 포함된 `references/` 양식을 매 호출 읽고 아래 항목을 유지한다. 구체 자산 파일명은 계획에서 정한다.

| 항목 | 작성 기준 |
|---|---|
| 문제 요약 | 한 문서에서 다루는 문제와 핵심 증상을 짧게 설명한다. |
| 기대/실제 동작 | 사용자의 기대와 실제 관측을 구분한다. |
| 환경·버전 | 확인 가능한 WB·OMP 버전, OS·terminal·외부 multiplexer 등 관련 환경을 기록한다. 확인하지 못한 값은 표시한다. |
| 발생 순서·재현 정보 | 사용자가 설명한 조작·발생 시점·빈도·기존 재현 여부를 기록한다. skill이 재현 실행을 했다고 꾸미지 않는다. |
| 영향 | 작업·입력·화면·데이터 등에 확인된 영향과 사용자 진술을 구분한다. |
| 증거·로그 | 관련 원문을 직접 포함하고 출처·시각·확인 가능한 Task/run/command 식별자, 가림·누락을 연결한다. 경로만 기록해 원문을 대신하지 않는다. |
| 원인 가설과 근거 | 관측 사실과 가설을 구분하고 근거를 연결한다. 근거가 없으면 원인 미확정으로 남긴다. |
| 이미 시도한 조치 | 사용자 설명 또는 기존 기록으로 확인한 조치와 결과를 적는다. 새 수정·재현을 수행하지 않는다. |
| 미확인·누락 정보 | 모르는 값, 접근 실패, 로그 잘림·소실·발췌 제한, 가림 사실을 표시한다. |
| 다음 조사 제안 | 후속 디버깅에서 확인할 사항을 적는다. 제안을 실행 승인으로 간주하지 않는다. |

양식의 고정 항목은 품질 기준이다. `미확인`을 허용하며, 양식이 있다는 이유로 원인이나 로그를 만들어 채우지 않는다.

## 구현 방향과 검증 의도

제품 지시문·reference·필요 최소 수집 지원을 기존 WB skill 구조에 맞춰 계획한다.
구현 파일별 소유권과 도구 인터페이스는 아직 확정하지 않았다. 새 자동 수집 service나
별도 agent의 도입을 전제하지 않는다. 기존 자료와 지원되는 읽기 인터페이스를 우선 확인한다.

계획·구현 단계의 검증 의도:
- 지원 OMP에서 Manager slash 노출·사용자 호출 성공, Worker 미노출,
  model 자동 선택 제외와 위임·알림 실행 제외를 확인한다.
- 같은 reference로 정상 자료·부분 자료·원인 미확정 보고서를 생성해 항목과 사실/가설 구분을 확인한다.
- 원래 파일에 접근할 수 없는 환경에서 Markdown만으로 포함된 증거를 읽을 수 있는지 확인한다.
- 민감정보가 있는 자료, 누락·rotation·발췌 제한 자료, 접근 거부에서 가림·누락 표시를 확인한다.
- 기존 파일 충돌과 저장 권한 오류에서 덮어쓰기 방지·대화 전문 제공을 확인한다.
- 보고서 생성이 수정·재현·복구·자동화 재개·외부 게시를 시작하지 않는지 확인한다.

이 절은 검증 의도이며 실제 runtime 통과나 제품/test 구현 권한이 아니다.

## 미결정·유보

사용자 동작을 막는 미결정 질문은 현재 없다. 다음은 계획·기술 검증에서 상세화한다.

1. OMP 18.11.1 및 계획에서 정한 지원 버전의 사용자 전용 호출 기능:
   과거 18.7.0 문서만으로 호환성을 확정하지 않는다. 자동 선택 제외와 slash 노출을
   함께 만족할 수 없다면 실패 근거와 대안을 사용자에게 제시한다. agent 자동 실행을 허용하는 식으로 약화하지 않는다.
2. 발췌·보고서 크기 기본값과 초과 처리: 제한과 생략을 표시하는 합의 안에서 정한다.
3. reference 자산 파일명, 출력 파일명의 구체 포맷·식별자 생성, 현재 프로젝트·data dir의
   안전한 식별, 기존 로그/상태의 읽기 경로: 계획에서 정한다. 식별할 수 없는 값을 추측하지 않고
   필요한 경로를 사용자에게 묻거나 해당 자료를 미확인으로 처리한다.
4. WB가 완전히 내려간 동안의 별도 reporter는 유보하며 이번 구현 범위에 포함하지 않는다.
