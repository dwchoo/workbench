# WB 작업 기록의 DB 저장과 Markdown 내보내기 — 요구사항 합의

Revision: r0.2; state: approved for planning (개별 결정 WR-D01~06과 추가 경계 WR-P01~05 전체 합의).
작성·확정일: 2026-10-20. 사용자가 최종 확인안에 “그렇게 해서 확정하자.”라고 답해 전체 BRIEF를 승인했다. 승인 reference·digest는 [승인 기록](approval.json), 개별 답변과 확인 이력은 [결정 기록](../../../.workflow/workbench-records/runs/refine-20261020/decisions.json)에서 관리한다. 이번 승인과 상태 문구 정리는 planning을 위한 합의이며 구현 권한이 아니다.

## 문제, 사용자와 목표

사용자는 WB에서 작업하다가 내용을 기록해 달라고 요청할 때, 연구 프로젝트의 `docs/` 등에 파일을 생성하는 대신 WB의 SQLite에 기본 저장하기를 원한다. Manager·Worker·다음 세션이 같은 기록을 저장·조회해 이어서 작업하고, 사용자가 요청할 때 Markdown으로 다른 위치에 남기는 것이 목표다.

## 공통 용어

[CONTEXT.md](../../../CONTEXT.md)의 WB 작업 기록, 작업 기록 revision, 기록 내보내기, WB 프로젝트 상태, Manager, Worker, Task, 중요 로그를 따른다. 자동 중요 로그는 출처에 연결된 보조 요약이며, 명시적으로 남기는 작업 기록과의 관계는 추가 합의 WR-P01에서 구체화한다.

## 범위와 비목표

- 포함: 메모·결정·진행 상황·실험 정리·인계 기록의 SQLite 기본 저장, Manager·Worker·다음 세션의 기록 저장·조회 공유, 사용자 요청에 따른 Markdown 내보내기.
- BRIEF·SPEC·ADR 같은 정식 프로젝트 문서는 기존 파일 방식을 유지한다. 이 discovery의 BRIEF와 용어집도 현행 저장소 개발 workflow에 따라 파일로 관리한다.
- 지시·질문·응답의 기존 전달 경로를 유지한다. DB를 새 메시지 queue나 실행 승인 경로로 바꾸지 않는다.
- 원문 terminal 로그 전체의 DB 이전, 기존 `docs/` 자료의 자동 수입·삭제, Phase 2는 이번 기록 기능의 범위가 아니다.
- 합의된 포함 범위에는 같은 프로젝트의 새 세션에 최근 기록 제목·짧은 미리보기 자동 제공, 필요 시 본문 조회, 이전 버전을 보존하는 revision 수정과 기본 최신본 조회도 포함한다.
- 프로젝트 메모와 Task 연결, 본문 보존·자동 요약의 관계, 조회 수단, 내보내기·실패 처리의 최소 경계는 최종 확인에서 채택한 WR-P01~05를 따른다.

## 제약과 호환성 약속

- Python 중심·Linux 우선, 기존 Manager/Worker 역할과 승인·pause·no replay·프로세스 수명 계약을 유지한다. 기록 열람·저장 자체를 새 실행 승인으로 해석하지 않는다.
- 기존 작업 metadata·명세·실행·결과와 중요 로그의 보존 계약을 변경하지 않는다. 이 합의는 raw rotation 활성화나 기존 로그 삭제 승인이 아니다.
- 프로젝트별 WB 상태 분리와 맞춘다. `.wb/` 기본 경로와 상태 이관은 [설치·사용 BRIEF](../workbench-installation/BRIEF.md)의 별도 discovery이며, 이 문서가 그 전체 승인이나 구현 완료를 뜻하지 않는다.
- 기존 [WB 문제 보고서](../workbench-problem-report/BRIEF.md)는 사용자 직접 호출로 Markdown 문서를 만드는 별도 산출물이다. 이번 합의로 그 계약을 변경하지 않는다.

## 합의된 공개 동작과 수락 예시

다음은 개별 사용자 결정과 전체 BRIEF 승인에서 도출한 수락 기준이다.

- WR-AC-01: 사용자가 WB에 작업 메모·결정·진행 상황·실험 정리·인계를 기록해 달라고 요청하면 기본 저장 대상은 WB SQLite다. 해당 요청만으로 프로젝트 `docs/`에 기록 파일을 만들지 않는다.
- WR-AC-02: 사용자가 기록을 Markdown으로 남겨 달라고 요청하면 다른 위치의 Markdown 파일로 내보낼 수 있다. 대상 선택·경로·기존 파일 충돌은 WR-P03을 따른다.
- WR-AC-03: 정식 BRIEF·SPEC·ADR의 작성·관리 요청은 기존 파일 기반 문서 workflow를 따른다. 작업 기록 DB로 기본 저장 대상을 바꾸지 않는다.
- WR-AC-04: Manager·Worker·같은 프로젝트의 다음 세션은 DB에 저장된 기록을 저장·조회하며 공유할 수 있다.
- WR-AC-05: 기록 공유를 추가해도 기존 지시·질문·응답 전달 경로를 DB 전송 경로로 교체하지 않는다.
- WR-AC-06: 같은 프로젝트의 새 세션을 시작하면 최근 기록의 제목과 짧은 미리보기를 자동 제공하고, 본문은 필요할 때 조회한다. 저장된 기록을 알려주는 동작이며 새 메모의 자동 작성을 뜻하지 않는다.
- WR-AC-07: 사용자가 기존 기록을 고쳐 달라고 요청하면 같은 기록의 새 revision으로 저장하고 이전 revision도 보존한다. 기본 조회는 최신 revision을 보여주며, 이전 revision도 확인할 수 있다.

### 최종 확인에서 채택한 최소 경계

WR-AC-08~12는 WR-P01~05에 각각 대응한다. 사용자의 전체 BRIEF 확정 답변으로 함께 채택되었으며, ID의 P는 제안 당시의 추적 식별자로 유지한다.

- WR-AC-08 / WR-P01: Task가 없는 메모는 프로젝트에 연결해 저장할 수 있고, 특정 작업에 관한 기록은 해당 Task와 연결한다. 저장 완료한 본문과 자동 중요 로그·요약을 구분한다. 미리보기·자동 요약이 저장된 본문을 대체하지 않는다. 별도 원문을 제공하지 않고 agent에게 정리를 요청한 경우에는 정리해 저장한 본문이 그 기록의 원본이다.
- WR-AC-09 / WR-P02: 같은 프로젝트에서 기록 목록, 제목·본문의 문자열 검색, 기록 ID별 본문·revision 조회를 제공한다. 새 세션에 제공할 최근 기록의 개수·미리보기 길이는 유한하게 정하고, 전체 본문·이력은 필요할 때 조회한다. 의미 검색·embedding·별도 검색 agent는 이번 범위에서 제외한다. 도구·CLI·화면의 구체 이름은 planning에서 정한다.
- WR-AC-10 / WR-P03: 사용자가 선택한 기록을 지정한 경로의 Markdown 파일로 내보낸다. 기본은 최신 revision이며 요청 시 보존된 특정 revision도 선택할 수 있다. 파일에 기록 ID·revision·기록 시각을 함께 남겨 출처를 확인할 수 있게 한다. 경로가 없으면 출력 경로를 확인하고, 기존 파일은 덮어쓰지 않고 충돌을 알려 다른 경로를 지정하게 한다. DB 기록은 유지하며, 내보낸 파일의 후속 수정을 DB에 자동 반영하지 않는다.
- WR-AC-11 / WR-P04: 작업 기록과 이전 revision을 자동 삭제하지 않는다. 기록 삭제·자동 정리, 기존 Markdown의 수입·이관, Markdown과 DB의 양방향 동기화는 이번 기능에서 제외한다. 기존 로그와 상태 이관 계약을 대체하지 않는다.
- WR-AC-12 / WR-P05: 저장·수정은 DB 저장 성공을 확인한 뒤 완료로 알린다. 저장 실패를 숨기거나 파일 저장으로 조용히 우회하지 않으며 이전 정상 기록을 보존한다. 지원 크기를 넘는 본문은 몰래 잘라 저장하지 않고 실패를 알린다. 조회 불가와 검색 결과 없음은 구분한다. 내보내기 실패 시 실패·경로를 알리고 DB 기록은 유지한다. 새 기록 기능의 실패가 기존 실행 승인 metadata의 장애 정책을 변경하지는 않는다.

WR-P01~05는 최종 확인에서 채택한 추가 합의다. 각각 Task 없는 메모와 본문 보존, 최소 조회 수단, 명시적 Markdown 사본 출력, 자동 삭제 제외, 실패 표시를 구체화한다. 프로젝트 메모를 Task에 억지로 귀속하지 않고, 요약·파일 출력 때문에 원본 의미가 달라지지 않도록 하기 위한 선택이다.

이 단계에서는 별도 ADR을 만들지 않았다. 기존 DB·문서 계약 전체를 대체하는 결정을 내리지 않으며, 기록 기능의 경계는 이 BRIEF에서 관리한다.

## 구현 방향과 검증 의도

구체 DB 파일·table·schema, 도구·CLI·UI 이름과 ticket 배치는 후속 planning에서 정한다. 기존 중요 로그의 요약 전용 계약에 임의 메모 저장이 이미 지원된다고 간주하지 않는다.

후속 planning·구현의 검증 대상은 저장 → 같은 프로젝트의 다른 역할·새 세션에서 목록·미리보기 확인 → 필요한 본문 조회 → 새 revision 저장·이전 revision 확인 → 요청한 Markdown 내보내기다. 기본 기록 요청이 `docs/` 파일을 생성하지 않는지, 정식 문서·기존 전달 경로가 유지되는지도 확인한다.

Task 없는 메모와 프로젝트 격리, 본문 검색, 자동 요약 후 원본 유지, 특정 revision 출력, 파일 충돌·DB 저장 실패·조회 불가·출력 실패도 해당 수락 예시에 맞춰 검증한다. 구체 schema·본문 크기 상한·최근 목록 개수·preview 길이와 동시 수정의 원자적 저장 방식은 이 경계를 지키는 planning 상세다. 제한 때문에 본문을 무음 유실하거나 타 프로젝트 기록을 혼합해서는 안 된다.

## 저장소 근거

기준: HEAD `f3eac23`, 2026-10-20 정적 읽기 조사. 실제 DB·모델·제품 실행은 하지 않았다.

- `src/workbench/storage/metadata_sqlite/schema.py`: Task·명세 revision·Run·결정·실행 event를 SQLite에 저장하는 schema가 있다.
- `src/workbench/storage/important_log/store.py`: 별도 SQLite 기반 중요 로그 저장 구조가 있다. 새 기록 기능과 동일한 원본·본문 계약이라는 근거는 아니다.
- `src/workbench/backend/summary_writer.py`: 요청에 결속된 요약 결과를 고정 host writer로 중요 로그 DB에 기록하는 코드가 있다. 임의의 사용자 기록 저장·조회·내보내기 흐름을 검증한 결과는 아니다.
- `src/workbench/contracts/logs_v1.py`의 `parse_important_body`: 기존 중요 로그 본문은 `facts`·`interpretations`·`unknowns` 배열의 계약이다. 일반 작업 기록 본문·revision이 이미 지원된다고 볼 수 없으며 같은 DB 파일이나 schema를 사용할지는 planning에서 판단한다.
- [개발 검증·로그 보관 BRIEF](../dev-validation-log-retention/BRIEF.md) LG-D24: 중요 로그의 목적은 작업 목적·범위, 결정과 이유, 수정·시도, 검증 결과, 미완료·다음 행동을 남기는 것이다. 기존 요약·보존·출처 계약과의 접점을 후속 planning에서 확인해야 한다.
- `graphify query "sqlite persistence record artifact handoff export context" --budget 2000`: 관련 시작점으로 TaskRepository와 core·로그 보관 BRIEF를 찾았다. 출력 일부가 잘렸으므로 위 파일을 직접 확인했다. 그래프 탐색은 실행 검증 근거가 아니다.

## 미결정·유보와 영향

- WR-Q01은 WR-D05, WR-Q02는 WR-D06으로 해소했다. 이미 확정한 선택을 다시 묻지 않는다.
- WR-Q03은 WR-P01·04, WR-Q04는 WR-P03·05의 채택으로 해소했다. 실질적으로 기록을 다시 찾을 수 있도록 WR-P02도 채택했다. 이번 범위에서 미결정인 제품 동작은 없다.
- 삭제·자동 정리·기존 Markdown 수입·양방향 동기화·의미 검색은 이번 계획에 넣지 않는다. 설치·프로젝트 상태 이관·기존 중요 로그·raw 정책은 별도 기능의 합의와 권한을 따른다.
- 상세 DB 배치·schema·조회 인터페이스와 유한한 입출력 한도는 후속 planning에서 구체화하되, 사용자에게 보이는 원본·revision·보존·오류 의미를 바꾸지 않는다. 실제 구현에 필요한 공개 OMP session 진입점·역할별 도구 노출의 가능성은 이번 정적 조사에서 검증하지 않았다.
