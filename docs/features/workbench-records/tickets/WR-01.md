# WR-01: OMP 세션 context·도구 노출의 최소 runtime 판별

명세: [SPEC.md s1](../SPEC.md). Scheduling·의존성·resource·write scope·gate supplier 정본: [PLAN.json p1](../PLAN.json)의 `WR-01` 항목. 상태·실제 assignment는 Root 운영 기록에서만 관리한다.

## 제공할 동작

실제 OMP의 주 Manager·Worker session에서 최근 기록 canary를 UI와 다음 provider context에 제공할 공개 경로를 판별한다. DB 없이 만든 synthetic 목록을 사용하므로 저장 모듈의 준비를 기다리지 않는다. Probe는 제품 기능의 완료가 아니다.

## 수락 기준

WR-AC-04·06의 선행 capability만 담당한다. PLAN의 WR-G01-context-capability는 실제 OMP runtime 근거가 필요하다. 전체 기록 공유·미리보기 수락은 WR-06/07이 별도로 확인한다.

## 계약과 근거

SPEC s1의 새 세션 미리보기·역할/subagent·추가 turn 없음 계약을 따른다. 기존 `bridge.ts`의 공개 lifecycle과 `tests/backend/q01_sdk_context_probe/context_extension.ts`의 sendMessage 사용례는 출발점이며 실제 startup/switch 동작의 증거는 아니다. 기존 OMP binary를 명시적으로 사용하고 설치/업데이트하지 않는다.

## 최소 판별 실험

가정: bridge 연결 뒤 custom message/동등 공개 hook으로 context를 제공하면서 추가 모델 turn을 만들지 않을 수 있다.

1. 임시 HOME·synthetic canary·localhost scripted provider를 준비한다. 두 주 역할에서 도구 등록/노출과 주 session identity를 관측한다.
2. Start 후 canary context를 `triggerTurn:false`로 제공한다. 사용자 입력 전 provider 요청이 새로 생기지 않는지, UI 표시 및 한 번의 자연스러운 입력에서 실제 provider payload에 canary가 들어오는지 확인한다.
3. 새 session switch·빠른 첫 입력·지연된 이전 응답을 따로 판별한다. Subagent가 주 역할 도구/preview를 쓰지 않는 경계를 확인한다. 연결 성공·API 반환·실제 context·UI 관측을 구분한다.
4. 각 실행은 유한한 connection/turn deadline을 사용하고 pipes/PTY를 비운다. 종료 시 정확한 소유 process만 정리하고 residue·cache·용량을 기록한다.

Passed면 API 이름·호출 순서·context payload·실제 roster와 소비 조건을 전달한다. Failed/inconclusive면 후속 OMP 확장을 막고 원인/다음 한정 실험을 기록한다. 함수가 존재하거나 mock test가 통과한 사실만으로 passed를 쓰지 않는다. 동등한 공개 hook 비교는 허용하지만 별도 자동 모델 turn·preview 제거·새 사용자 조작을 해결책으로 확정하지 않는다.

## 검증

예정 명령: `WB_LIVE_RECORDS=1 PYTHONPATH=src python3 -m unittest tests.backend.work_records.live_session_context_probe`.

예상값은 DB/제품 구현에서 가져오지 않은 고정 canary·session ID와 provider 요청 목록이다. 이 ticket은 필요한 feasibility probe이므로 제품 동작의 TDD 대신 가정→작은 실험→결과→후속 범위의 순서를 기록한다. test_designer는 판별력·음성 대조·timeout 해석을 독립 평가하고 U1 fresh general review를 적용한다. Gate 수준·supplier 정본은 PLAN이다.

## 비목표와 중단 조건

제품 저장/조회 코드를 작성하지 않는다. 사용자 인증·실제 OMP home/DB·유료 provider·Docker·새 설치는 사용하지 않는다. 소유 실행 환경/기존 OMP를 사용할 수 없으면 해당 근거를 pending/not_run으로 남긴다. Broken probe의 timeout을 OMP 결함으로 단정하지 않는다.

## 허용 변경과 출력 handoff

계획의 `write_scope_hint` 안에서 동작과 검증을 함께 작성한다. 테스트를 전부 먼저 쓰거나 구현/테스트를 서로 다른 worker에 일괄 분리하지 않는다. Root는 dispatch 때 실제 기반 후보·TDD reference identity·공개 seam·허용 경로·명령을 재확인한다. Scope 확대가 필요하면 변경 전에 이유와 영향을 전달한다. 동시 writer는 검증된 격리 workspace와 호환 resource가 있을 때만 허용한다.

Candidate ID·변경 경로·정확한 command/result·독립 expected value·미검증 한계와 각 행동의 RED 원인/당시 후보→최소 변경→GREEN 후보/명령을 전달한다. Probe/문서 등 정당한 예외는 이유·대체 근거를 남긴다. 결과는 candidate_ready/needs_reroute/needs_oracle/blocked 중 실제 상태와 근거를 사용하며 그 flag만으로 통합·수락을 주장하지 않는다. Commit·게시·배포하지 않는다.
