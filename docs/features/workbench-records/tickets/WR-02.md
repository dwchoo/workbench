# WR-02: 원문·Task 연결·revision의 SQLite 저장

명세: [SPEC.md s1](../SPEC.md). Scheduling·의존성·resource·write scope·gate supplier 정본: [PLAN.json p1](../PLAN.json)의 `WR-02` 항목. 상태·실제 assignment는 Root 운영 기록에서만 관리한다.

## 제공할 동작

고정 records-v1 계약과 별도 records SQLite 저장소를 만든다. 프로젝트 메모와 실제 Task 연결, create/revise/get 및 재열기 후 본문·과거 revision 보존을 제공한다. 다른 기록 모듈이 소비할 get/revision 계약을 먼저 확정한다.

## 수락 기준

WR-AC-01·07·08·11·12 중 로컬 저장/보존을 담당한다. Agent 기본 저장 선택·중요 로그 결합·실제 프로젝트 간 공유는 후속 결합 검사로 남긴다. Local gate는 WR-G02-durable-revisions다.

## 계약과 근거

SPEC s1의 별도 `records.sqlite3`, 한도, Task 연결, expected_revision, private path·schema·revision 오류 계약을 따른다. 기존 metadata/important DB에 메모 table을 추가하지 않는다. `DataLayout`에 고정 path accessor만 추가한다. 중요 로그 writer/retention/metadata hold 계약은 변경하지 않는다.

Create는 revision 1, revise는 전체 snapshot과 일치하는 expected_revision에서만 다음 버전을 만든다. `get(id, revision=None)`은 최신 또는 명시한 보존 snapshot을 반환하는 frozen seam이다. 이 계약의 검증본을 후속 조회·export가 독립적으로 소비한다. Task 연결 확인은 기존 공개 Task 조회를 사용하고 null인 프로젝트 메모에 불필요한 Task 생성을 요구하지 않는다.

## 검증

Worker는 한 행동의 public RED→최소 GREEN 뒤 다음으로 진행한다. 최초 저장/재열기, 과거/최신 조회, Task 없는 기록과 실제 Task, 과거 버전 보존, expected_revision 충돌, 저장 실패·크기 초과·schema/경로 불가를 구분한다. 실제 임시 SQLite·두 독립 connection으로 경합을 관측하며 최종 파일의 존재만으로 durable 성공을 판단하지 않는다.

예상값은 직접 작성한 한글·Markdown·인용부호·개행 본문, revision 1/2와 sentinel DB 내용이다. Contract fixture는 SPEC에서 독립적으로 적고 Python/TS 양쪽으로 확인한다. 본문64 KiB 경계와 UTF-8 byte 수를 별도 검증한다.

예정 명령:

- `PYTHONPATH=src python3 -m unittest tests.contracts.test_records_v1`
- `PYTHONPATH=src python3 -m unittest tests.storage.work_records.test_store`
- `node --experimental-strip-types --no-warnings --test tests/bridge/work_records_contract.test.ts`
- `PYTHONPATH=src python3 -m unittest tests.backend.test_paths_launcher`

Test seam은 실제 `RecordStore.create/revise/get`이며 OMP/실제 도구 노출을 입증하지 않는다. U2 test_designer 독립 평가와 fresh general review 뒤 frozen 계약을 통합한다. 새 SQL/path 입력 경계는 최종 별도 security review packet에 남긴다.

## 비목표와 중단 조건

목록/검색·CLI·bridge·Markdown·state migration을 이 ticket에 끌어오지 않는다. Worker가 Task schema나 core 승인 의미를 바꿔야 한다면 Root로 되돌린다. 기존 사용자 DB로 schema를 시험하지 않는다. get/revision 의미를 변경하면 후속 구현을 열기 전에 계약 영향과 승인 범위를 대조한다.

## 허용 변경과 출력 handoff

계획의 `write_scope_hint` 안에서 동작과 검증을 함께 작성한다. 테스트를 전부 먼저 쓰거나 구현/테스트를 서로 다른 worker에 일괄 분리하지 않는다. Root는 dispatch 때 실제 기반 후보·TDD reference identity·공개 seam·허용 경로·명령을 재확인한다. Scope 확대가 필요하면 변경 전에 이유와 영향을 전달한다. 동시 writer는 검증된 격리 workspace와 호환 resource가 있을 때만 허용한다.

Candidate ID·변경 경로·정확한 command/result·독립 expected value·미검증 한계와 각 행동의 RED 원인/당시 후보→최소 변경→GREEN 후보/명령을 전달한다. Probe/문서 등 정당한 예외는 이유·대체 근거를 남긴다. 결과는 candidate_ready/needs_reroute/needs_oracle/blocked 중 실제 상태와 근거를 사용하며 그 flag만으로 통합·수락을 주장하지 않는다. Commit·게시·배포하지 않는다.
