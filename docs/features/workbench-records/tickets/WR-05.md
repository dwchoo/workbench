# WR-05: Manager·Worker의 기록 도구 연결

명세: [SPEC.md s1](../SPEC.md). Scheduling·의존성·resource·write scope·gate supplier 정본: [PLAN.json p1](../PLAN.json)의 `WR-05` 항목. 상태·실제 assignment는 Root 운영 기록에서만 관리한다.

## 제공할 동작

검증된 저장·조회·export를 `workbench_records`라는 하나의 essential G3 도구로 제공한다. Manager와 Worker의 주 session이 같은 project store를 사용하며 host가 layout·actor·session identity를 정한다. Workbench logs/handoff/terminal의 기존 계약은 유지한다.

## 수락 기준

WR-AC-01·04·05·07·08·09·10·12의 agent 도구 경로를 담당한다. Local gate WR-G05-tool-roundtrip은 실제 UDS와 대체 OMP API 수준이며, 실제 lifecycle/context 전체를 통과시킨다는 뜻은 아니다.

## 계약과 근거

SPEC s1의 records-v1 action/nullable fields/status·Task 연결·한도·오류를 따른다. `_tool_request`에는 별도 branch와 작은 `RecordService`를 연결하고 기존 tool route를 재작성하지 않는다. `requestHandoff`의 session/generation·한 번 전송·결과 불명과 subagent 차단을 재사용한다. Worker allowlist에는 새 custom 이름만 더한다. 내장 shell/eval·subagent 권한·요약 SDK child의 도구를 확대하지 않는다.

WR-01의 실제 관측 API와 두 주 역할 roster 경계를 소비한다. WR-01이 failed/inconclusive면 관련 구현을 확장하지 않는다. 새 세션 preview·지침은 후속 ticket이 담당한다.

## 검증

Worker는 한 동작의 public RED→최소 GREEN을 반복한다. 독립 fixture로 create/revise/list/search/show/history/recent/export 요청을 실제 UDS로 통과시킨다. 서로 다른 두 role의 같은 ID 조회·actual Task/null Task·잘못된 session/generation·subagent 거절을 관측한다. Timeout/disconnect에서 한 번만 전송되고 unknown인 쓰기를 자동 replay하지 않는지 확인한다. 도구 결과의 `saved`는 DB 재조회와 맞아야 한다.

예정 명령:

- `PYTHONPATH=src python3 -m unittest tests.backend.work_records.test_service tests.bridge.test_work_records_extension`
- `node --experimental-strip-types --no-warnings --test tests/bridge/work_records.test.ts`
- `PYTHONPATH=src python3 -m unittest tests.bridge.test_handoff_tools_extension`

Expected value는 손으로 정한 wire fixture·한글 본문·ID·revision/status와 이전 tool 경로의 sentinel이다. Production handler 내부 호출 횟수만으로 수락하지 않는다. U4의 독립 test_designer는 이 local seam과 후속 실제 OMP seam을 구분한다. Local fixture gate·독립 평가 후 WR-06에 통합하고, U4 전체가 안정되면 fresh general review를 받는다.

## 비목표와 중단 조건

도구를 새 지시/승인 전달 경로로 사용하지 않는다. Backend 임의 SQL·DB/root 경로를 model 입력으로 받지 않는다. 사용자 auth나 실제 DB로 시험하지 않는다. 선행 runtime 판별이 무효화되거나 역할·승인 의미를 바꿔야 하면 Root에 구체 근거를 전달한다.

## 허용 변경과 출력 handoff

계획의 `write_scope_hint` 안에서 동작과 검증을 함께 작성한다. 테스트를 전부 먼저 쓰거나 구현/테스트를 서로 다른 worker에 일괄 분리하지 않는다. Root는 dispatch 때 실제 기반 후보·TDD reference identity·공개 seam·허용 경로·명령을 재확인한다. Scope 확대가 필요하면 변경 전에 이유와 영향을 전달한다. 동시 writer는 검증된 격리 workspace와 호환 resource가 있을 때만 허용한다.

Candidate ID·변경 경로·정확한 command/result·독립 expected value·미검증 한계와 각 행동의 RED 원인/당시 후보→최소 변경→GREEN 후보/명령을 전달한다. Probe/문서 등 정당한 예외는 이유·대체 근거를 남긴다. 결과는 candidate_ready/needs_reroute/needs_oracle/blocked 중 실제 상태와 근거를 사용하며 그 flag만으로 통합·수락을 주장하지 않는다. Commit·게시·배포하지 않는다.
