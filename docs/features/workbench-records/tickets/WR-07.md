# WR-07: 전체 흐름·보존·이관·설치본 통합 검증

명세: [SPEC.md s1](../SPEC.md). Scheduling·의존성·resource·write scope·gate supplier 정본: [PLAN.json p1](../PLAN.json)의 `WR-07` 항목. 상태·실제 assignment는 Root 운영 기록에서만 관리한다.

## 제공할 동작

Root가 최종 결합 후보를 통합·검증한다. 기존 중단 상태 `wb migrate`의 inventory/schema/논리 내용 검증에 records DB 보존만 확장하고, 두 역할·두 프로젝트·재시작·설치본에서 전체 흐름을 확인한다. USAGE/README에 합의된 사용법을 남긴다. 제품 변경이 필요한 좁은 부분은 지정 worker가 작성하고 Root가 직렬 통합한다.

## 수락 기준

WR-AC-01~12 전체와 PLAN의 WR-G08-preservation-migrate, WR-G09-live-flow, WR-G10-installed-assets, WR-G11-final-review를 담당한다. 앞선 local/runtime gate도 최종 후보에 유효한지 대조한다. 각 gate의 owner/supplier·evidence level은 PLAN 정본을 따른다.

## 계약과 근거

SPEC s1의 보존·프로젝트 분리·기존 전달·상시 지침·preview·CLI/export·호환을 모두 유지한다. `backend/migrate.py`는 현재 신규 파일을 unknown으로 거절하므로 명시적으로 records DB·journal을 인식하고 read-only schema/내용 검증·기존 snapshot/복사 경로로 보존하게 한다. 이관 방식·실행 중 거절·원본 보존·대상 충돌·기존 Task/로그/인증 계약을 바꾸지 않는다. 실제 사용자 저장소를 이관하는 작업이 아니다.

배포 자산은 기존 `build_support/assets.py` 경로를 먼저 확인한다. 새 TS/Python 자산이 이미 수집된다면 불필요한 packaging 변경을 하지 않는다. 실제 누락이 관측될 때만 해당 범위를 수정한다. 상세 저장소 스키마와 신규 파일 인식은 이 migration 호환에 한해 다룬다.

## 검증

새 migration 호환 동작은 public RED→최소 GREEN으로 개발한다. Source에 기록이 있는/없는 임시 legacy store에서 원본·현재/과거 revision·기존 DB/로그를 대조하고, 새 project marker를 가진 target에서 실제 조회를 확인한다. 비정상 schema·활성 owner·충돌 target의 기존 거절도 유지한다.

실제 WB/OMP·localhost scripted provider·임시 HOME와 DB로 create→다른 역할 조회→revise→새 session preview→검색→지정 revision export→process 재시작 조회를 실행한다. 서로 다른 프로젝트는 다른 sentinel을 사용한다. 중요 로그 요약·maintenance 후에도 작업 기록 원문·revision이 남아야 하며 raw 삭제 정책을 활성화하지 않는다. Docs의 일반 메모 파일 미생성과 정식 문서/문제 보고서의 기존 계약도 확인한다.

예정 명령:

- `PYTHONPATH=src python3 -m unittest discover -s tests/storage/work_records -p 'test_*.py'`
- `PYTHONPATH=src python3 -m unittest discover -s tests/backend/work_records -p 'test_*.py'`
- `node --experimental-strip-types --no-warnings --test tests/bridge/work_records.test.ts tests/bridge/work_records_context.test.ts`
- `PYTHONPATH=src python3 -m unittest discover -s tests/backend/installation -p 'test_*.py'`
- `PYTHONPATH=src python3 -m unittest discover -s tests/backend/workbench_report -p 'test_*.py'`
- `WB_LIVE_RECORDS=1 PYTHONPATH=src python3 -m unittest tests.integration.live_workbench_records`
- `WB_LIVE_RECORDS=1 PYTHONPATH=src python3 -m unittest tests.integration.live_workbench_records.InstalledAssetsTests`

설치본은 기존 installation harness의 소유 비editable build/venv·지정 OMP recipe를 확장해 저장소 밖 임시 프로젝트에서 확인한다. Recipe가 없거나 필요한 local tool이 없으면 pending/not_run을 기록하고 설치·외부 service를 자동 도입하지 않는다. 설치 근거를 checkout 기반 fixture로 대체하지 않는다.

Expected value는 test가 직접 정한 원문·revision·ID·시각·프로젝트별 sentinel·기존 DB/로그 hash다. 설치본/실제 OMP 관측과 모델 자연어 품질은 구분한다. Independent test_designer는 요구에서 새로 시나리오를 도출하고 의미 있는 worker coverage를 평가한다. 필수 checks가 통과한 frozen code+tests에 fresh Standards·Spec reviewer 두 context, 별도 security reviewer와 deterministic diff secret scan을 적용한다. Accepted delta는 영향에 맞는 확인만 반복하고 무변경 후보의 전체 review를 반복하지 않는다.

## 비목표와 중단 조건

Live 이관·병합·기존 기록 삭제·양방향 동기화·의미 검색·기존 raw 정책 변경·새 dependency를 추가하지 않는다. 유료 provider·사용자 인증/실제 DB·서비스·외부 tmux 설정을 쓰지 않는다. Local/runtime/설치본 중 하나가 필수 수준 미달이면 완료로 표시하지 않는다. 승인된 제품 동작을 바꿔야 하는 실패는 Root가 근거와 한정 결정 요청으로 다룬다.

## 허용 변경과 출력 handoff

계획의 `write_scope_hint` 안에서 동작과 검증을 함께 작성한다. 테스트를 전부 먼저 쓰거나 구현/테스트를 서로 다른 worker에 일괄 분리하지 않는다. Root는 dispatch 때 실제 기반 후보·TDD reference identity·공개 seam·허용 경로·명령을 재확인한다. Scope 확대가 필요하면 변경 전에 이유와 영향을 전달한다. 동시 writer는 검증된 격리 workspace와 호환 resource가 있을 때만 허용한다.

Candidate ID·변경 경로·정확한 command/result·독립 expected value·미검증 한계와 각 행동의 RED 원인/당시 후보→최소 변경→GREEN 후보/명령을 전달한다. Probe/문서 등 정당한 예외는 이유·대체 근거를 남긴다. 결과는 candidate_ready/needs_reroute/needs_oracle/blocked 중 실제 상태와 근거를 사용하며 그 flag만으로 통합·수락을 주장하지 않는다. Commit·게시·배포하지 않는다.
