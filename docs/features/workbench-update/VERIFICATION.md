# 업데이트 검증 근거

승인 기준은 BRIEF b1/SPEC s1/PLAN p1이다. 이 문서는 관측 결과만 기록하며 승인 기준을 바꾸지 않는다.

WU-01은 실제 private uv noneditable local Git 설치의 두 commit으로 실행 중 Python의 자기 교체와 flock 수명을 관측했다. 실제 `uv` 성공 exit 0, invalid ref exit 2, 새 interpreter의 commit/entrypoint/assets, 실패 보고 중 SIGINT/EOF를 확인했다. timeout descendant cleanup은 별도 RED→GREEN으로 보완했다. 이 결과는 후속 updater의 실제 설치 통합 성공을 대신하지 않는다.

WU-02에서는 공개 `cli.main` update/start 및 기존 shutdown controller seam을 검증했다. targeted 13개, 기존 start/설치 경계 39개, shutdown 영향 3개가 통과했다. uv/Git·설치 metadata·backend IPC와 process inventory는 외부 경계 fixture를 사용했고, snapshot filesystem·SQLite·hash·flock 및 소유 helper process는 실제였다.

WU-03은 외부 사용자 backend가 host에 존재하므로 host에서 실행하지 않았다. 기존 Linux `unshare --user --map-root-user --pid --fork --mount-proc`와 private tmpfs `/tmp`를 사용했다. harness가 host와 다른 PID namespace, PID 1, 단일 UID mapping, 해당 namespace의 `/proc`, private `/tmp`, 예상치 못한 기존 fence/runtime 부재를 확인한 뒤 시작한다. 실제 uv/Git와 SHA256을 확인한 기존 OMP 18.11.1 binary, private HOME/XDG/cache/DB, loopback scripted provider만 사용했다. 사용자 backend·auth·DB·global tool을 조작하지 않았다. Docker·새 도구 설치·외부 provider·실제 모델 호출은 없었고, 실제 OMP의 HTTP 요청 네 번에는 로컬 고정 응답을 반환했다.

실제 설치 통합 `WU03-live-a5`는 exit 0이었다. 실제 noneditable uv Git 설치의 이전 commit `2357dbd38ffee1d0a3cc46ac82e61779fe17e4f2`에서 목표 `4342f3eaa70b74b51d069499a02a9faff07cc91c`으로 자기 교체했다. 두 private 프로젝트에 실제 manager/worker session, 두 Task spec revision, manager/worker 기록 원문 두 revision, 실행·승인 이력, raw 및 source/result sentinel을 만들었다. host shell의 실제 진행 명령 PID/start ticks를 관측하고, TTY 거절 exit 1 때 명령 생존·pause/승인/기록 보존·백업 부재를 확인했다. TTY 승인 exit 0 뒤 정확한 종료, stopped 원본과 백업의 포함 파일 hash·mode 일치, credential/cache 제외, 새 interpreter의 commit·entrypoint·asset 확인을 통과했다. 재시작은 일시정지와 이전 session 원문을 유지했고, 명령 실행 횟수는 한 번이며 자동 재실행·새 모델 turn이 없었다.

같은 실행의 대표 설치 실패는 최종 설치에만 비어 있는 private uv cache를 제공해 실제 offline uv exit 1을 만들었다. 준비·종료·백업은 완료됐고 manifest는 설치 상태 `unknown`·`complete=false`, 실제 exit, 이전/목표 commit과 백업을 보존했다. 실패 안내에 수동 재설치가 있었으며 성공으로 표시하지 않았다. 이 한 사례로 모든 uv 실패가 이전 설치를 보존한다고 보장하지 않는다.

초기 실패도 보존했다. a1/a2는 live SQLite header의 정상 counter flush까지 byte 불변으로 요구한 harness 오류였다. 두 파일의 counter bytes 27·95만 바뀌고 DB 내용·기록은 같음을 진단한 뒤 그 header 항목만 구분했다. a3/a4는 기존 공용 harness가 read-only SQLite connection을 `with` 종료 후 닫지 않아 WAL/SHM writable FD를 남긴 문제였다. 제품은 writer 잔존을 올바르게 거절했다. 별도 실제 SQLite probe로 원인을 확인하고 connection을 명시적으로 닫았다. 제품의 writer 거절을 완화하지 않았으며, 실패 진단에는 고정된 내부 거절 사유만 추가했다.

후속 과거 ref 회귀는 공개 `cli.main` test의 RED→최소 GREEN으로 고쳤다. 종료 이전 준비 단계에서 staged target의 공개 `start`를 현재 exclusive fence 아래 실행한다. 명시적 missing OMP와 미생성 private data 경로로 실제 backend 실행을 막으며, fence 거절을 확인하지 못하면 작업 종료 전에 거절한다. `WU03-preflight-a1`의 실제 준비 전용 실행은 현재 target의 start exit 1/fence 거절과 canonical `a6d877fa3d38f04d816c2f105f131a9be93fdac1` payload의 start exit 2/OMP 부재를 구분했다. 양쪽 모두 data 경로를 만들지 않았고 설치된 이전 commit은 그대로였다. 이는 신뢰하는 WB ref의 호환성 검사이며 임의 Git 코드를 안전하게 실행하는 sandbox 보장이 아니다.

이 준비 단계 변경 뒤 targeted 14개가 통과했다. 전체 두 프로젝트 실험을 반복하지 않고, a5의 변경 없는 종료·백업·자기 교체·재시작·실패 경계를 이월했다. 실행 당시 packaging inputs와 harness SHA256, namespace command·환경·exit·raw log·정리 상태는 `.workflow/workbench-update/runs/implement-p1-20261020/WU03-result.json` 및 각 `input-hashes.json`에 연결했다. 모든 소유 process 종료와 private root 제거를 확인했고 namespace 종료로 private `/tmp`도 사라졌다. 실제 외부 Git 인증·원격 서버·사용자 설치나 데이터는 검사하지 않았다. Root의 독립 Standards/Spec/Security 검증 및 최종 결합 검사는 별도이다.

후속 독립 검사는 종료 동의 경계의 두 결함을 검출했다. 기존 token/TTL만 확인하는 구버전 backend가 표시한 작업 A 대신 바뀐 작업 B를 종료할 수 있었고, 현재 backend도 자신의 shutdown hold 뒤 실제 controller tick이 같은 experiment를 `active → held`로 표시하면 잘못 거절했다. 원래 독립 RED를 유지한 채, 현재 server의 scope-bound 종료 지원 표시와 updater의 구버전 거절, 표시 상태와 구분한 automation run·work·process identity 비교로 각각 GREEN을 확인했다. 독립 test 파일은 수정하지 않았으며 변경 Task/run/process 거절도 유지했다. 최종 기존·독립 maintenance 26개가 통과했다.

client/server IPC가 바뀌었으므로 수정 후 `Final-fix-live-a1`에서 같은 실제 두 프로젝트 lifecycle을 격리 환경에서 한 번 다시 실행했고 exit 0이었다. 실제 이전 commit `768463d7ed2475f06058aa333dbf4211e4d21428`에서 목표 `f8fcb6f75563a2990ea31566e49a77d64d538545`으로 교체했으며 TTY 거절·승인, 원문/revision/session 백업, 일시정지 재시작·자동 replay 부재, 실제 offline uv 실패 exit 1의 미확인 상태 보고를 통과했다. 전체 packaging inputs와 양 harness hash가 최종 source와 일치한다. own-hold의 정확한 controller tick interleave는 독립 실제 controller 검사에서 다뤘고, 설치 통합에서는 실제 공개 client/server 종료 경로를 확인했다. 실행 command·환경·SHA·raw log 및 소유 process 종료/private root 제거 근거는 같은 run의 `Final-fix-result.json`에 연결했다. 최종 독립 검토와 전체 완료 판정은 Root가 수행한다.

최종 review의 세 결함도 각각 실제 RED→최소 GREEN으로 보완했다. manual background 작업이 동의 목록에서 빠졌고, 같은 shell의 foreground A가 B로 교체돼도 이전 동의가 유효했으며, WB 내부 updater caller가 자신의 shutdown에 종료될 수 있었다. 종료 조회에서만 shell session jobs의 PID/start ticks·process group과 PTY foreground group을 새로 읽어 표시·signature에 결합하고, 관측 불명은 idle로 처리하지 않는다. caller는 검증한 backend/process identity와 자신의 ancestry/session이 겹치거나 확인이 불명이면 어떤 backend 종료보다 먼저 외부 terminal 안내와 함께 거절한다. detached runner나 자신만 제외하는 종료 프로토콜은 추가하지 않았다.

`Final-work-live-a1`의 단일 실제 격리 실행은 exit 0이었다. 실제 WB host shell에서 실행한 updater가 backend 종료·백업 없이 거절됐고, 실제 background job을 표시한 TTY 거절 후 job이 생존했다. 실제 동의 화면을 읽은 뒤 foreground A를 끝내고 B를 시작하자 이전 동의로 B를 종료하지 않았고, manifest는 `installation=not_started`·백업 미완료·종료 결과 없음이었다. 새 동의에서는 foreground와 background를 모두 종료하고 이전 commit `f3153c6a180daee065014fed18159d50be706399`에서 목표 `ed29904cb2c81bab5e4c45574d9bd5681f9215e7`으로 실제 교체했다. 기존 두 프로젝트의 원문/revision/session·backup·paused 재시작·자동 replay 부재와 실제 uv 실패 exit 1도 같은 실행에서 확인했다. 모든 소유 process 종료/private root 제거를 확인했다. 실행 당시 packaging inputs·harness SHA·command·환경·raw 결과는 같은 run의 `Final-work-fix-result.json`에 연결했다.

현재 feature maintenance 29개가 통과했다. 추가 affected 묶음에서는 shell kill/exit 경계 3개와 실제 Bash/dash manual-input 2개가 통과했다. 함께 실행한 이전 `test_cli_shutdown_wait_cw16`은 11개 test의 15개 error subcase가 기존 `Layout` double의 `record` 부재로 실패했다. `Final-work-affected-shell.log`에 원본을 보존했고, Root의 `Root-baseline-cli-fixture.log`가 published HEAD에서도 같은 오류를 확인했다. 해당 기존 CLI identity seam·fixture는 이번 변경 범위 밖이라 수정하지 않았으며 이 묶음 전체를 통과로 표시하지 않는다. Root의 추가 broad backend 검사도 `Root-final-backend-check.json` 기준 300초 timeout·exit -9·source stable·소유 process 잔존 0인 미완료 검사다. feature 및 affected-boundary의 개별 통과 근거와 구분하며 전체 backend 통과를 주장하지 않는다.
