# Task scripts and visible progress

Apply when creating or editing task code. The manager writes task code; the worker only runs it. Staged `response_contract` replies remain marker-only, with no tools.

- No multi-purpose scripts. Plan the work as units that one simple command or one short script can do, and write one script per unit in `<project-root>/.wb/scripts/` (save reusable code and project deliverables in the appropriate project directory). Reuse a suitable existing script. Resolve paths from the project root, regardless of terminal cwd or `--data-dir`.
- Write a shell script, or a Python script run with `uv run` that declares its dependencies inline (PEP 723), for example a header `# /// script`, `# dependencies = ["tqdm"]`, `# ///`. Inline dependencies stay in uv's cache, not the project environment.
- Ask the user before any install or setup that changes the environment (system or project packages, virtual environments, global tools, configuration) and wait for the approval. Once the user approves, continue that same kind of install or setup for the rest of this manager session without asking again; ask again for a different kind.
- Save code before running it. Do not embed a whole program in `python -c`, a heredoc or a long shell command. Workbench's automatic command wrapping does not replace a maintained script. Short read-only queries and ordinary shell commands need no script.
- Manager: authorize script paths in `spec.paths` and list file-based execution commands. Correct conflicting procedures before delegation; update paths/commands explicitly for follow-ups. Worker: never write or edit task code; if a script is missing, wrong or not authorized, report `blocked` and ask the manager. Never bypass the allowlist with inline code.
- Keep the simplest implementation for today's task. Parameterize run-varying inputs/outputs through arguments or existing configuration. Avoid machine-specific paths, credentials and duplicated logic. Keep useful defaults/constants; add no speculative framework, plugin system or abstraction.
- Long-running code must show its state on one line updated in place (`tqdm`, or carriage return plus flushing): percent, elapsed time and ETA. With an unknown total, show the actual count or stage and the elapsed time, never invented percentages. Never print a new line per step or interval that scrolls the terminal, and never leave it looking stalled. Throttle updates; show errors/warnings separately and finish with a success/failure summary and newline. Non-interactive output uses sparse milestones. Do not rewrite a quick query or external command just to add a progress bar.
